---
description: 从当前 GitHub 项目的代码、配置、入口和依赖中反推缺失的关键文档，输出最小必要文档清单。
---

对当前 GitHub 项目做一次“缺失文档审计”。

目标不是补齐所有文档，而是找出：

1. 哪些**关键知识**目前没有被文档化
2. 哪些知识虽然有文档，但**覆盖不足**
3. 哪些内容**根本不值得写文档**

最终输出一份“最小必要文档清单”，只补真正值得维护的文档。

## 扫描范围

默认扫描当前 GitHub 项目的仓库根目录：

1. 先执行 `git rev-parse --show-toplevel`
2. 若成功，则以 git root 为扫描范围
3. 若失败，则使用当前目录
4. 若用户传入路径 `$ARGUMENTS`，则优先扫描该路径

排除目录：

`node_modules/`, `.git/`, `.svn/`, `.hg/`, `dist/`, `build/`, `coverage/`, `.venv/`, `venv/`, `__pycache__/`, `.next/`, `.nuxt/`, `.claude/`, `.idea/`, `.vscode/`

优先关注文件类型：

- 代码文件：如 `.py`, `.ts`, `.tsx`, `.js`, `.jsx`, `.go`, `.java`, `.sh`, `.bat`
- 配置文件：如 `.json`, `.yaml`, `.yml`, `.toml`, `.ini`, `.env`, `.properties`
- 文档文件：如 `.md`, `.mdx`, `.txt`, `.rst`, `.adoc`

## 产出物

- `docs/docs-gap-report.md`：缺口审计报告

## 核心原则

- **只补高价值知识，不补低价值说明**
- **优先补“AI 无法稳定从代码推断出来”的知识**
- **优先建议合并到现有核心文档，而不是新建很多文档**
- **能用代码注释解决的，不强行升格为文档**
- **目标是最小文档集，不是完整文档集**

---

## Phase 1: 识别项目中的知识源

先从代码与配置中识别“潜在需要文档化的知识源”。

重点扫描：

1. **入口文件**
   - 主程序入口
   - CLI
   - batch / shell 脚本
   - scheduler / cron / workflow 触发点

2. **关键配置源**
   - 环境变量读取点
   - 配置文件路径
   - feature flag
   - 多运行模式切换

3. **外部依赖**
   - 数据库连接
   - 第三方 API
   - 文件系统路径
   - 消息系统
   - webhook / 回调

4. **核心业务规则实现**
   - 日期决策
   - 状态机
   - 去重 / 幂等 / 覆盖逻辑
   - 默认值 / 回退逻辑
   - 金额、阈值、排序、过滤规则

5. **数据契约**
   - 核心表
   - 核心字段
   - 状态值 / 枚举值
   - 时间口径
   - 主键 / 唯一键 / join 关键字段

6. **模块边界**
   - 哪些模块是 orchestration
   - 哪些模块是核心规则
   - 哪些模块是适配层

---

## Phase 2: 识别已有文档覆盖情况

检查当前文档是否已经覆盖这些知识源。

覆盖情况只分四类：

| 状态 | 含义 |
|------|------|
| `covered` | 已有文档充分覆盖，且位置合理 |
| `partial` | 有文档，但覆盖不完整、不集中或不够权威 |
| `missing` | 明显缺失，没有文档承载这类知识 |
| `no-doc-needed` | 不值得专门写文档，代码本身足够自解释 |

### 覆盖判断标准

只有在以下条件同时满足时，才算 `covered`：

- 能找到承载该知识的文档
- 文档内容不是一句带过
- 文档位置合理，后续容易被找到
- 文档足以支持 AI 或维护者稳定理解该知识

若只是零散提了一嘴，算 `partial`，不算 `covered`。

---

## Phase 3: 判定哪些知识值得补文档

不是所有 gap 都值得补。

### 高价值知识

以下知识类型优先考虑补文档：

1. **系统目标与边界**
2. **运行入口与主流程**
3. **关键业务规则 / 不变量**
4. **外部依赖契约**
5. **数据契约**
6. **模块职责边界**
7. **历史兼容 / 已知坑点**
8. **验证改动是否正确的方法**

### 低价值知识

以下内容通常不值得专门补文档：

- 逐文件介绍
- 纯目录树
- 函数级 API 逐条复述
- 从代码中一眼能看出的常规实现细节
- 无需跨文件理解的简单工具函数说明

### 决策问题

对每一个 gap，回答：

> 如果没有这份知识说明，AI 或维护者是否会高概率改错代码、改错位置、或者误判系统边界？

判定：

- `yes`：这是高价值 gap，应补
- `maybe`：可补可不补，优先考虑合并进已有核心文档
- `no`：不要补文档

---

## Phase 4: 给出最小补文档方案

对每个应补的 gap，不要默认新建文档。

优先级顺序如下：

1. **合并进根 README**
2. **合并进已有核心文档**
3. **新增一页短文档**
4. **只补代码注释**
5. **不补**

### 文档形态建议

| 形态 | 适用场景 |
|------|---------|
| README 小节 | 项目级边界、启动方式、主入口 |
| 单页核心文档 | 关键规则、数据契约、外部依赖契约 |
| 短文档 | 独立但高价值的复杂主题 |
| 代码注释 | 局部规则、特殊分支、坑点 |

如果一个 gap 只需要 5 到 15 行说明，优先建议“并入现有文档”，不要建议新建一整页。

---

## Phase 5: 重点检查哪些缺口最危险

将 gap 按风险排序。

### 🔴 高风险 gap

满足任一条件：

- 不写清楚就容易改错主流程
- 不写清楚就容易误解关键业务规则
- 不写清楚就容易漏掉外部依赖前提
- 不写清楚就容易破坏数据口径
- 新人或 AI 很难仅靠代码稳定恢复该知识

### 🟡 中风险 gap

- 有一定理解成本
- 代码里能拼出来，但费时且容易遗漏上下文
- 适合并入现有文档而不是单独成文

### 🟢 低风险 gap

- 不补也问题不大
- 补代码注释即可
- 代码已足够自解释

---

## Phase 6: 生成缺口报告

写入 `docs/docs-gap-report.md`。

报告结构如下：

```markdown
# 文档缺口审计报告

> 生成时间: {datetime}
> 扫描范围: {path}

## 摘要

- 已充分覆盖: {n}
- 覆盖不足: {n}
- 明显缺失: {n}
- 不建议补文档: {n}

## 一、最应该补的关键知识

| 知识主题 | 风险级别 | 证据来源 | 当前状态 | 建议补法 |
|---------|---------|---------|---------|---------|

## 二、已有文档但覆盖不足

| 知识主题 | 当前文档 | 不足之处 | 建议动作 |
|---------|---------|---------|---------|

## 三、完全缺失的高价值文档

| 知识主题 | 为什么重要 | 代码证据 | 建议补法 |
|---------|-----------|---------|---------|

## 四、不建议补文档的内容

| 知识主题 | 原因 |
|---------|------|

## 五、最小必要文档集建议

只给出最终建议保留/新增的最小集合，例如：

- README：补充系统边界 + 主入口 + 启动方式
- docs/business-rules.md：集中记录关键业务规则
- docs/external-contracts.md：集中记录环境变量 / 数据库 / 外部路径契约
- 某模块代码注释：补充特殊分支原因
```

无内容的章节直接删除，不保留空表。

---

## 最终输出给用户的摘要

报告完成后，只向用户展示：

1. 最值得补的 3 个知识缺口
2. 最不值得补文档的 3 类内容
3. 建议形成的“最小必要文档集”
4. 完整报告路径

然后告知完整报告已写入：

`docs/docs-gap-report.md`

---

## 守护栏

- **不是找“还没写的所有东西”**
- **只找“值得写但没写”的关键知识**
- **优先建议合并，而不是新增很多页面**
- **不要为了完整而完整**
- **拿不准时，优先建议补短文档或代码注释**
- **输出中文**
