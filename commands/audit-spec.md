按项目规范 v1.0 检查当前项目的合规性，逐项报告缺失和不符合项，提供修复方案。

## 规范全文

以下是完整的项目规范，作为检查基准：

---

### 1. README 规范

每个项目根目录必须包含 `README.md`，按以下 6 个章节组织：

**必须包含的章节：**

1. **项目介绍** — 一句话定位 + ASCII 架构图 + 运行模式列表 + 业务规模
2. **快速启动** — 分 4 个子节：
   - 需要安装什么（表格：依赖 / 版本要求 / 安装方式 + 复制即用命令 + 已知坑）
   - 需要配置什么（分步骤：cp 命令 + 必填/可选表格 + 默认值）
   - 启动命令（每种模式的完整命令）
   - 如何验证结果（SQL 查询 / 预期输出 / 文件路径）
3. **项目配置文件说明** — 总览表格（配置文件 / 位置 / 用途 / 是否必须修改）+ 逐个展开（字段表格 + 格式示例）
4. **项目工作流程图** — ASCII 流程图 + 阶段划分 + 函数名标注 + 多模式对比表
5. **数据库说明** — Schema 总览表 + 表清单（表名 / 说明 / 关键字段 / 更新频率）+ 初始化命令
6. **项目目录结构** — tree 格式 + 每行标注模块职责

**编写原则：**
- 不写废话
- 配置项必须有示例值和默认行为说明
- 流程描述用阶段划分，标注函数名和数据流向
- 验证手段要具体：给 SQL 语句、预期行数、文件路径
- 表格优先、ASCII 图优先

---

### 2. 配置文件管理

- 敏感配置（密码、API Key）只能放 `.env`，禁止硬编码
- 必须提供 `.env.example`（占位符 + 注释分组 + 默认行为说明）
- JSON/YAML 含敏感信息的必须有 `.example` 版本
- `.gitignore` 忽略真实配置，用 `!` 保留 example
- 加载优先级：`.env 环境变量 > JSON/YAML 配置文件 > 代码内默认值`
- **表名/配置键常量化**：代码中引用的数据库表名、配置键等标识符禁止散落硬编码在业务代码中，必须集中管理。推荐做法（按优先级）：
  1. 从已有配置文件（如 YAML DDL 定义）自动读取，代码中通过配置键引用
  2. 建立常量模块 `global_setting/db_constants.py`，统一定义所有表名常量，业务代码 import 使用
  3. 如果表名仅在 1-2 处使用且不会变更，可在函数顶部定义局部常量并加注释说明
- **硬编码自查清单**：以下内容不应出现在业务逻辑代码中，应提取到配置文件或常量模块：
  - 数据库表名、库名
  - 时间阈值（开盘/收盘时间、定时任务触发点）
  - 连接池参数（连接数、超时时间）
  - 业务阈值（过滤条件、分位数步长、权重容差）

---

### 3. .gitignore 规范

必须覆盖：
- 敏感配置（.env）+ 保留 example（!*.example.*）
- Python（__pycache__/ *.py[cod] .venv/ venv/）
- 日志（*.log log/）
- 临时文件（*.tmp）
- IDE（.idea/ .vscode/ *.swp）
- Claude Code（.claude/ .claude.zip）
- 数据目录（data/）
- OS（.DS_Store Thumbs.db）

---

### 4. 数据库 SQL 规范

- SQL 文件统一放 `sql/` 目录：schema/（编号前缀）、migration/（日期前缀）、seed/
- 每表有头部注释（表名 / 用途 / Schema）
- 每字段有 COMMENT
- 使用 CREATE TABLE IF NOT EXISTS

---

### 5. 项目文档规范

- 文档放 `doc/` 目录
- 根目录只保留：README.md（必须）、TODO.md（必须）、.env.example（必须）
- TODO.md 格式：`- [ ] 做什么 —— 为什么`，完成后打勾

---

### 6. 项目目录结构规范

**Python 项目：**
- 入口脚本放根目录，`run_` 前缀
- 业务模块按职责拆分独立目录
- 工具函数统一放 `utils/`
- 必须有：pyproject.toml / uv.lock / .python-version
- 使用 uv 管理依赖

**Python + MATLAB 混合：**
- MATLAB .m 文件放对应 Python 模块内的 `matlab/` 子目录
- 通过配置文件指定当前使用的 MATLAB 函数版本

---

### 7. CLAUDE.md 规范

- 全局（~/.claude/CLAUDE.md）：称呼、结束符、包管理器、MATLAB 路径、Docker 规则、待办追踪、远程服务器
- 项目级（项目根目录 CLAUDE.md）：技术栈、运行方式、注意事项（已知坑和约束）、关键路径

---

## 检查流程

### 第 1 步：扫描项目

读取项目根目录，识别：
- 语言、框架、包管理器
- 已有的配置文件和文档
- 目录结构
- .gitignore 内容
- README.md 结构
- CLAUDE.md 是否存在

### 第 2 步：逐项对照

按规范 7 个章节，逐项检查是否符合。每项标记 ✅（通过）、⚠️（部分符合）、❌（缺失/不合规）。

### 第 3 步：输出报告

输出一张状态总表：

| # | 规范项 | 状态 | 问题 |
|---|--------|------|------|
| 1 | README 结构 | ✅/⚠️/❌ | 具体缺什么 |
| 2 | 配置文件管理 | ... | ... |
| ... | ... | ... | ... |

### 第 4 步：修复清单

按优先级列出需要修复的项目：

- **P0（必须修复）**：敏感信息泄露、缺少 .gitignore、缺少 .env.example
- **P1（建议修复）**：README 缺少章节、缺少 CLAUDE.md、TODO.md 格式不对
- **P2（可选优化）**：缺少 pre-commit、SQL 文件未归档、doc/ 目录不存在

每项附带具体的修复命令或内容建议。

### 第 5 步：询问用户

展示报告后，询问用户是否需要逐项修复。得到确认后再动手修改。

## 守护栏

- 只检查不修改，修复前必须经用户确认
- 不编造项目没有的文件或配置
- 不确定的信息询问用户
- 检查结果基于实际文件，不靠猜测
