---
description: 从当前项目代码库逐文件穷举业务规则，生成三层业务规则文档（说明书 + 取证底稿 + 追溯矩阵）
argument-hint: [--output-dir docs] [--verify-only]
---

从当前项目代码库中**逐文件精读**，穷举提取全部业务规则，生成三份独立文档：

1. **business-rules.md** — 给人读懂系统的业务说明书
2. **business-rules-evidence.md** — 逐文件取证底稿
3. **br-inventory.md** — 规则索引与追溯矩阵

## 输入参数

- **codebase**: 当前工作目录（自动获取）
- **--output-dir**: 输出目录（默认 `docs`）
- **--verify-only**: 跳过提取，对已有三份文档做四向交叉验证 + 一致性检查 + 自动补全（会修改文档）

## 核心原则

1. **逐文件，不跳过** — 按文件遍历，每个文件都看，不凭经验猜测哪些文件"不重要"
2. **提取，不编造** — 每条规则必须能指向代码中的具体位置
3. **三层分离** — 说明书给人读、底稿做审计、矩阵做追溯，职责不混
4. **业务视角优先** — 先让人看懂，再让人追溯
5. **交叉验证** — 提取完成后必须做四向交叉验证 + 两项一致性检查

## 三份文档的职责

| 文件 | 一句话职责 | 读者 |
|------|----------|------|
| `business-rules.md` | 给人读懂系统 | 业务方、新人、写 spec/test 的人 |
| `business-rules-evidence.md` | 证明"这不是编的" | 审计、二次验证、代码变更时回查 |
| `br-inventory.md` | 从源码查规则，从规则查源码 | 验证覆盖率、写 spec 时追溯 |

---

## 执行流程

### Phase 1: 扫描代码库

列出当前工作目录的完整目录结构，识别**全部包含业务逻辑的源文件**。

**扫描范围（显式定义）：**
- **必须纳入的文件类型**：`.py`、`.m`（MATLAB）、`.sql`、`.sh`、`.bat`（含业务编排的脚本）、`.yaml`/`.json`（含业务路由或阈值配置的）
- **判定标准**：文件中包含 if/else 业务判断、计算公式、数据过滤、硬编码常量、执行顺序编排中的任意一种，即为核心业务文件
- **排除**：`tests/`、`docs/`、`__pycache__/`、`*.pyc`、日志配置桩（仅 logging.setLevel）、纯类型定义文件、第三方库、备份/副本文件（匹配模式：文件名含"副本"、或以 `_ori`/`-ori`/`.ori` 结尾/分隔、或含 `.backup`/`_backup`/`-backup`、或以 `_old`/`-old`/`.old` 结尾/分隔；注意不要误伤含 ori/old 子串的合法文件如 optimizer、history）

**执行步骤：**
1. 遍历目录树，按上述规则分为"核心文件"和"排除文件"两组
2. 核心文件按**执行流程顺序**排列（入口 → 数据准备 → 核心计算 → 输出 → 持久化）
3. 输出文件清单供确认：

```
## 代码库扫描

路径: [当前工作目录]

核心文件（按执行顺序）:
1. run_main.py           — 主流程编排 (.py)
2. data_prepared.py      — 数据准备 (.py)
3. optimizer_func_v2.m   — 优化求解核心 (.m)
4. ...

排除文件（含排除理由）:
- tests/test_xxx.py      — 测试代码
- data_prepared - 副本.py — 备份文件
- logger_setup.py        — 纯日志配置
```

### Phase 2: 逐文件精读 → 产出取证底稿

**对每个核心文件**，精读并提取业务规则证据。

提取粒度（与 v1 相同）：

| 提取对象 | 成为证据的条件 |
|---------|--------------|
| if/else 分支 | 基于业务条件的判断 |
| 计算公式 | 涉及业务量的运算 |
| 数据过滤 | 排除/筛选特定记录 |
| 校验规则 | 合法性检查 |
| 硬编码值 | 业务常量/阈值 |
| 数据源选择 | 根据条件读不同表 |
| 输出格式 | CSV/DB 的列定义和取值 |
| 执行顺序 | 步骤间的依赖关系 |
| 特殊处理 | 硬编码的排除/覆盖 |

**每个文件的证据格式（写入 evidence.md）：**

```markdown
## 文件: Tracking/running_main.py

文件角色: Tracking 模块主循环与时段控制

| # | 行号 | 证据摘要 | 提取出的规则 | 分类 |
|---|------|---------|------------|------|
| 1 | 55-60 | `hour==9 and minute<35` 下清空 `realtime_*` 表 | 开盘前清空实时结果表 | 时段控制 |
| 2 | 65-67 | `hour >= 16` 触发 historySql_saving | 收盘后归档到历史表 | 时段控制 |
| 3 | 214 | `time.sleep(30)` | 实时循环间隔 30 秒 | 执行频率 |
```

**evidence.md 末尾放以下独立 section**（不混入主文档）：
- **遗留/非主链代码说明** — 已检查但判定为非当前生效的代码
- **已知问题与潜在 Bug** — 提取过程中发现的代码疑点
- **排除文件说明** — 被排除的文件及排除理由

### Phase 3: 按业务域组织 → 产出业务说明书

将 Phase 2 提取的规则按**业务域**归类，用以下模板写成可读的业务说明书。

**BR section 模板：**

```markdown
## BR-XX: [业务域名称]

[一句话说明这个域解决什么业务问题]

### BR-XXa: [规则名称]

触发条件:
- [什么时候、什么条件下触发]

输入:
- [需要什么数据]

处理规则:
1. [步骤化描述核心逻辑]
2. [关键公式 + 数值例子]
   例(说明性): stock_money=10,000,000, weight=0.05, close=1680
   → 目标金额=500,000 → 股数=297.6 → 取整=300股

边界与例外:
- [异常路径、特殊处理、时间窗口限制]

输出:
- [产出什么结果/写什么表/生成什么文件]

来源:
- Trading/holding_construct.py:67-91
```

**模板使用规则：**
- **"目的"必填** — 每个 BR section 开头必须有一句话说明这个域解决什么业务问题，每个子规则（BR-XXa）开头的"触发条件/输入"等字段按需使用
- **关键公式必须配数值例子**，区分两种来源：
  - 代码中有测试数据或注释示例 → 直接引用，标注为 `例(源码)`
  - 代码中无示例 → 可自拟说明性演算，但必须标注为 `例(说明性)` 且不得伪装成源码事实
- **"来源"始终压到每节末尾**，不在规则描述中穿插行号
- **只写当前生效规则**，遗留/非主链/已知 Bug 不进主文档

**business-rules.md 结构：**

```markdown
# [系统名称] 业务规则说明书

> 最后更新: YYYY-MM-DD
> 取证底稿: [business-rules-evidence.md](business-rules-evidence.md)
> 追溯矩阵: [br-inventory.md](br-inventory.md)

---

## 系统概览

[简述系统做什么、包含哪些模块、日常执行时序]

[ASCII 数据流图：从数据进来到最终产出]

---

## BR-01: [第一个业务域]
...

## BR-02: [第二个业务域]
...

---

## 附录 A: 数据依赖汇总

### 内部表
| 表名 | 角色 | 读/写 | 模块 |

### 外部数据
| 数据 | 用途 | 来源 |

## 附录 B: 常量与阈值
| 常量 | 值 | 用途 | 来源 |
```

### Phase 4: 生成追溯矩阵

从 Phase 2 的每一条证据生成 inventory 记录，并标注映射关系：

```markdown
# BR Inventory 追溯矩阵

> 生成时间: YYYY-MM-DD
> 证据来源: [business-rules-evidence.md](business-rules-evidence.md)
> 规则文档: [business-rules.md](business-rules.md)

## 追溯表

| INV ID | 来源文件:行号 | 规则摘要 | → BR 编号 | 状态 |
|--------|-------------|---------|----------|------|
| INV-0001 | update_main.py:88-97 | 日更顺序 Mkt→Score→Factor→Macro→L4→Check | BR-01a | 已收录 |
| INV-0002 | running_main.py:55-60 | 9:00-9:34 清空 7 张 realtime 表 | BR-07a | 已收录 |
| INV-0003 | Mktdata_update.py:494 | 8*/43* 开头永久不可交易 | — | 未映射 |

## 覆盖率统计

| 维度 | 数量 |
|------|------|
| 证据总数 | N |
| 已映射到 BR | M |
| 未映射 | N-M |
| BR 总数 | K |
| 有证据支撑的 BR | J |
| 无证据的 BR | K-J |
```

### Phase 5: 四向交叉验证 + 一致性检查

**这一步不可跳过。**

重新逐文件阅读代码，同时做四向交叉检查 + 两项一致性检查：

**四向交叉检查：**

| 检查方向 | 发现什么问题 | 处置 |
|---------|------------|------|
| 代码 → evidence | 代码中有逻辑但 evidence 表没记录 | 补入 evidence.md |
| evidence → inventory | 有证据但没编 INV 号 | 补入 br-inventory.md |
| inventory → BR | 有 INV 但没映射到 BR | 归类到对应 BR 或标"未映射" |
| BR → evidence | BR 中有描述但没有 evidence 支撑 | 要么补 evidence，要么删除该 BR（不编造） |

**两项一致性检查：**

| 检查项 | 发现什么问题 | 处置 |
|-------|------------|------|
| BR 内部自相矛盾 | 同一业务域内的规则互相冲突（如 BR-03a 说"取整到百"但 BR-03c 说"不取整"） | 回查代码确认哪个正确，修正错误的那条 |
| 主链混入遗留/旁支 | business-rules.md 中混入了非当前生效的逻辑（注释掉的代码、dead code 路径） | 移出主文档，归入 evidence.md 的"遗留/非主链代码说明" section |

**验证输出：**

```
## 交叉验证结果

### 补充项
| # | 方向/检查项 | 发现 | 处置 |
|---|------------|------|------|
| 1 | 代码→evidence | running_main.py:214 sleep(30) 未提取 | 补入 evidence |
| 2 | inventory→BR | INV-0003 未归入任何 BR | 新增 BR-18f |
| 3 | 内部矛盾 | BR-03a 与 BR-03c 取整规则冲突 | 回查代码，修正 BR-03c |

### 覆盖率
- evidence 条目: N 条 → 全部编入 inventory
- inventory → BR 映射率: M/N (xx%)
- BR 条目: K 条 → 全部有 evidence 支撑
- 内部矛盾: 0 处（已修正）
- 遗留混入: 0 处（已清理）

验证结论: 补充 X 条，三份文档已同步更新
```

### Phase 6: 产出物

写入 `--output-dir` 指定目录（默认 `docs/`）下的三个文件：

1. **`business-rules.md`** — 业务说明书（主文档）
2. **`business-rules-evidence.md`** — 取证底稿
3. **`br-inventory.md`** — 追溯矩阵

---

## `--verify-only` 模式

当三份文档已存在，仅执行 Phase 5（四向交叉验证 + 两项一致性检查 + 自动补全）：

1. 读取已有三份文档
2. 重新逐文件阅读代码
3. 做四向交叉检查 + 两项一致性检查
4. 补全遗漏，输出验证报告

**编号稳定性要求：** 已有的 BR-XX 和 INV-XXXX 编号不得重排。新增规则追加到对应业务域末尾（如 BR-03 域已有 a/b/c，新增编为 BR-03d）；新增 INV 从已有最大编号递增。删除规则时编号作废不回收，不做整篇重编号。

输出前逐项检查：

- [ ] 每个 BR section 有一句话"目的"开头（必填）

- [ ] "来源"压在每节末尾，不穿插在规则描述中
- [ ] 只包含当前生效规则，无遗留/Bug 混入
- [ ] 不看代码也能理解每条规则
- [ ] 常量表和数据依赖作为附录保留

**business-rules-evidence.md：**
- [ ] 每个核心文件都有对应的证据表
- [ ] 每条证据标注了行号和分类
- [ ] 遗留代码和已知问题在独立 section，不混入文件证据表
- [ ] 排除文件有说明理由

**br-inventory.md：**
- [ ] 每条 evidence 都有对应的 INV 编号
- [ ] 每条 INV 都标注了 BR 映射状态
- [ ] 覆盖率统计数字正确
- [ ] "未映射" 条目已确认是有意排除还是遗漏

**交叉验证：**
- [ ] 四向交叉检查已完成
- [ ] 两项一致性检查已完成（无内部矛盾、无遗留混入主链）
- [ ] 无 BR 条目缺少 evidence 支撑
- [ ] 未映射的 INV 已确认处置

## 守护栏

- **不跳文件** — 每个核心业务文件必须完整阅读
- **不编造** — 只提取代码中实际存在的逻辑
- **不混层** — 说明书里不插行号表格，底稿里不写业务解释散文
- **不简化公式** — 关键公式保留完整表达式并配数值例子
- **四向验证 + 一致性检查不可跳过** — 这是从"大概率完整"到"零遗漏"的关键步骤
- **编号只增不重排** — 已有的 BR-XX 和 INV-XXXX 编号不得重新编排，新增追加、删除作废不回收
- **保持人间清醒** — 对自己的提取结果保持怀疑
