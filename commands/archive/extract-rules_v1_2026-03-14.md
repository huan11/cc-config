从当前项目代码库中**逐文件精读**，穷举提取全部业务规则，生成一份**独立完整、零知识丢失**的业务规则文档。

在写任何 spec 或测试之前，先确保对系统的业务逻辑有 100% 的理解。

## 输入参数

- **codebase**: 当前工作目录（自动获取，无需手动指定）
- **--output**: 输出文件路径（默认 `docs/business-rules.md`）
- **--verify-only**: 仅执行二次验证（跳过提取，对已有文档做完整性校验）

## 核心原则

1. **逐文件，不跳过** — 按文件遍历，每个文件都看，不凭经验猜测哪些文件"不重要"
2. **提取，不编造** — 每条规则必须能指向代码中的具体位置
3. **独立完整** — 产出的文档自包含，不需要配合代码才能理解
4. **二次验证** — 提取完成后必须做第二轮逐文件回查，找出遗漏

## 执行流程

### Phase 1: 扫描代码库

1. 列出当前项目的目录结构，识别核心业务文件（排除测试、配置模板、静态资源等非业务文件）
2. 对核心文件按**执行流程顺序**排列（入口 → 数据准备 → 核心计算 → 输出 → 持久化）
3. 输出文件清单，确认扫描范围：

```
## 代码库扫描

路径: [当前工作目录]
核心文件（按执行顺序）:
1. run_main.py          — 主流程编排
2. data_prepared.py     — 数据准备
3. holding_construct.py — 持仓构建
4. ...

排除: tests/, docs/, __pycache__/, *.pyc
```

### Phase 2: 逐文件精读提取

**对每个核心文件**，按以下粒度提取业务规则：

| 提取对象 | 成为 BR 的条件 | 例子 |
|---------|---------------|------|
| if/else 分支 | 基于业务条件的判断 | `if account_money == "auto"` |
| 计算公式 | 涉及业务量的运算 | `target = round(money × weight / price / 100) × 100` |
| 数据过滤 | 排除/筛选特定记录 | `df = df[df["code"][:2] != "20"]` |
| 校验规则 | 合法性检查 | `if not 0.97 < weight_sum < 1.03: raise` |
| 硬编码值 | 业务常量/阈值 | `threshold = 500000` |
| 数据源选择 | 根据条件读不同表 | 标准产品 vs L4 产品 |
| 输出格式 | CSV/DB 的列定义和取值 | `方向: 0=买入, 1=卖出` |
| 执行顺序 | 步骤间的依赖关系 | 先保存组合 → 再生成订单 |
| 特殊处理 | 硬编码的排除/覆盖 | `排除 688256.SH` |

**每提取一个文件，输出：**

```
### [文件名] (行范围)

| # | 行号 | 规则描述 | 分类 |
|---|------|---------|------|
| 1 | :32-56 | 交易日 15:00 前→当天，15:00 后→下一交易日 | 日期决策 |
| 2 | :60-80 | 只处理 is_active=1 的产品 | 产品管理 |
```

### Phase 3: 归类整理

将所有提取的规则按**业务领域**归类为 BR section：

1. 对相关规则分组（如"资金计算"、"权重合成"、"订单差异"等）
2. 每组编为一个 BR-XX
3. 子规则编为 BR-XXa/b/c
4. 梳理边界情况和常量

**输出文档结构：**

```markdown
# 业务规则清单

> 来源: [代码库路径] 逐文件精读提取
> 零遗漏目标: 涵盖全部 [系统名称] 的业务逻辑
> 最后更新: YYYY-MM-DD

---

## BR-01: [领域名称]
- 规则描述...

### BR-01a: [子规则]
- 详细逻辑...

### BR-01b: [子规则]
- ...

## BR-02: ...

---

## 数据依赖汇总

### 内部表
| 表 | 角色 | 读/写 |

### 外部数据
| 数据 | 用途 | 来源 |

---

## 常量与阈值
| 常量 | 值 | 用途 |
```

### Phase 4: 二次验证（关键！）

**这一步不可跳过。** 第一轮提取必然有遗漏。

方法：重新逐文件阅读代码，逐行比对已提取的规则清单，找出：

1. **未提取的规则** — 代码中有但文档中没有的业务逻辑
2. **描述不精确** — 提取了但细节不够（如时机、顺序、特殊处理）
3. **隐含依赖** — 规则之间的执行顺序或数据流向未记录

**验证输出：**

```
## 二次验证结果

| # | 文件 | 发现 | 处置 |
|---|------|------|------|
| 1 | trading_order_jinxin.py | 金欣只输出CSV不写DB | 补入 BR-12 |
| 2 | portfolio_saving.py | 执行顺序: 先保存后交易 | 新增 BR-13a |
| 3 | — | — | — |

验证结论: 补充 N 条，文档已更新
```

### Phase 5: 产出物

1. **业务规则文档** — 写入 `--output` 指定路径（默认 `docs/business-rules.md`）
2. **BR Inventory（可选）** — 如果用户需要追溯矩阵，额外生成 `docs/br-inventory.md`

```
## BR Inventory 追溯矩阵

| # | 来源 | 规则描述 | BR 编号 | 状态 |
|---|------|---------|--------|------|
| 1 | run_main.py:32 | 15:00 切换 | BR-10 | ✅ |
```

## `--verify-only` 模式

当文档已存在，仅执行 Phase 4（二次验证）：

1. 读取现有 `docs/business-rules.md`
2. 重新逐文件阅读代码
3. 逐行比对，找出文档中缺失的规则
4. 输出验证报告 + 自动补全

## 质量检查清单

输出前逐项检查：

- [ ] 代码库每个核心文件都已逐行阅读（不是 grep 关键字）
- [ ] 每条 BR 能指向代码中的具体文件和行号
- [ ] 文档自包含（不需要读代码就能理解每条规则）
- [ ] 计算公式写出了完整的表达式（不是"按某种方式计算"）
- [ ] 硬编码常量全部列入常量表
- [ ] 数据依赖（表、列、外部数据源）全部列出
- [ ] 执行顺序和阶段依赖关系已记录
- [ ] 二次验证已完成，差异已补入文档
- [ ] 边界情况已记录（空输入、零值、缺失数据等）

## 与其他命令的关系

```
/extract-rules  → 从当前项目穷举提取业务规则（零知识丢失文档）
/gen-scenarios  → 从业务规则生成 GWT 功能测试场景
/absorb         → 从对话中提取知识沉淀到文件
```

**典型工作流：**
1. `/extract-rules` → 产出 `docs/business-rules.md`
2. `/gen-scenarios docs/business-rules.md` → 基于 BR 生成功能测试场景 spec
3. TDD 实现 → 每个场景对应测试 → 代码
4. `/extract-rules --verify-only` → 验证 spec 是否全覆盖

## 守护栏

- **不跳文件** — 每个核心业务文件必须完整阅读，不凭经验假设某文件"不重要"
- **不编造** — 只提取代码中实际存在的逻辑，不推测"应该还有"的规则
- **不简化** — 业务规则文档必须保留完整细节（公式、阈值、特殊处理），不做任何抽象简化
- **二次验证不可跳过** — 这是从"大概率完整"到"零遗漏"的关键步骤
- **保持人间清醒** — 对自己的提取结果保持怀疑，不轻易声称"零遗漏"
