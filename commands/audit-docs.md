---
description: 审计当前 GitHub 项目的文档，识别真正重要的知识，并检查这些知识是否仍与代码一致，输出可执行的精简/更新建议。
---

对当前 GitHub 项目的文档做一次“面向 AI 使用”的审计。

目标不是保留更多文档，而是找出：

1. 哪些文档包含**重要知识**
2. 这些重要知识是否仍然**与代码一致**
3. 哪些文档是**噪音、重复、过期或可归档**

最终输出一份可直接执行的文档审计报告，帮助后续做“少即是多”的文档清理。

## 扫描范围

默认扫描当前 GitHub 项目的仓库根目录：

1. 先执行 `git rev-parse --show-toplevel`
2. 若成功，则以 git root 为扫描范围
3. 若失败，则使用当前目录
4. 若用户传入路径 `$ARGUMENTS`，则优先扫描该路径

排除目录：

`node_modules/`, `.git/`, `.svn/`, `.hg/`, `dist/`, `build/`, `coverage/`, `.venv/`, `venv/`, `__pycache__/`, `.next/`, `.nuxt/`, `.claude/`, `.idea/`, `.vscode/`

扫描文件类型：

`**/*.md`, `**/*.mdx`, `**/*.txt`, `**/*.rst`, `**/*.adoc`

## 产出物

- `docs/docs-audit-report.md`：主报告
- `docs/docs-inventory.tsv`：文档清单

## 核心原则

- **只保留高价值知识**
- **重点检查“文档是否仍然正确”**
- **能从代码稳定推断出的信息，不值得单独维护**
- **文档服务于 AI 和维护者，噪音越少越好**
- **只读审计，不修改任何现有文档**

---

## Phase 1: 发现所有文档

建立完整文档清单，并为每个文档收集：

| 字段 | 获取方式 |
|------|---------|
| 相对路径 | 文件扫描 |
| 文件大小 | `wc -c` |
| 行数 | `wc -l` |
| 最后修改时间 | `stat` |
| 标题 | 前 10 行内首个标题或首行 |
| 所在目录 | 路径分析 |

将结果写入 `docs/docs-inventory.tsv`。

如果文档总数 > 200，先输出文档数量和目录分布，再继续。

---

## Phase 2: 文档归类

对每份文档做用途归类。归类的目标不是为了展示，而是为了后续判断“是否值得保留”。

### 一级类别

| 类别 | 定义 |
|------|------|
| `core-knowledge` | 可能包含项目的重要知识，值得重点检查 |
| `supporting` | 辅助说明文档，有一定价值但通常不是核心 |
| `snapshot` | 一次性分析、盘点、审计、取证、迁移快照 |
| `vendor` | 第三方文档、导入目录中的文档、依赖库说明 |
| `noise-candidate` | 大概率可删除、归档或合并的低价值文档 |

### 二级知识类型

如果文档可能属于 `core-knowledge`，继续标记知识类型：

| 知识类型 | 说明 |
|---------|------|
| `system-boundary` | 系统目标、范围、非目标 |
| `entrypoints-flow` | 运行入口、主流程、调度链路 |
| `business-rules` | 关键业务规则、不变量、算法约束 |
| `external-contracts` | 外部系统依赖、环境变量、数据库、文件路径、第三方服务 |
| `data-contracts` | 表结构语义、字段口径、主键、时间口径、状态值 |
| `module-boundaries` | 模块职责边界、分层、哪些逻辑放哪里 |
| `pitfalls` | 已知坑点、历史兼容、不能轻易改动的特殊逻辑 |
| `operations` | 启动方法、测试方法、发布/运行方式 |

### 归类启发式

以下文档通常优先视为 `core-knowledge`：

- 根 `README`
- `docs/` 下的总览、架构、运行、配置、数据库、入口、迁移说明
- 标题中含：`架构`、`入口`、`运行`、`数据库`、`配置`、`约束`、`规则`、`mapping`、`contract`

以下文档通常优先视为 `snapshot`：

- 标题或正文含：`分析报告`、`审计`、`盘点`、`取证`、`生成时间`、`扫描目录`
- 文件名含日期，如 `*-2026-04-14.md`

以下文档通常优先视为 `noise-candidate`：

- 逐文件介绍
- 纯目录树
- 与代码高度重复的函数文档
- 无引用的临时笔记
- 明显过时的阶段性记录

---

## Phase 3: 识别“重要知识”

对 `core-knowledge` 和部分 `supporting` 文档，判断其是否包含值得保留的重要知识。

### 判定标准

重要知识 = **代码里不容易稳定推断出来，但一旦理解错就会导致错误修改的知识**

### 高优先级重要知识

重点识别以下内容：

1. **系统目标与边界**
2. **运行入口与主流程**
3. **关键业务规则 / 不变量**
4. **外部依赖契约**
5. **数据契约**
6. **模块职责边界**
7. **历史兼容 / 已知坑点**

### 保留价值判定

对每份文档回答这个问题：

> 删掉这份文档后，只靠读代码，AI 是否还能稳定做对修改？

判定规则：

| 判定 | 含义 |
|------|------|
| `high-value` | 不能稳定做对，文档应保留并重点校验 |
| `medium-value` | 能做对但成本高，建议合并压缩 |
| `low-value` | 大概率能做对，属于噪音候选 |

---

## Phase 4: 检查重要知识是否与代码一致

这是本次审计的核心。

仅对 `high-value` 与部分 `medium-value` 文档做深度检查。

### 检查维度 1: 入口与流程是否一致

核对：

- 文档写的入口文件是否存在
- 文档写的主调函数是否仍存在
- 文档描述的调用链是否仍成立
- 文档描述的运行模式是否与当前代码一致
- 文档写的脚本 / batch / CLI 用法是否仍可对应到现有代码

若不一致：

- 关键入口错误 = 🔴
- 次要流程描述偏差 = 🟡

### 检查维度 2: 关键规则是否一致

识别文档中的业务规则描述，例如：

- 日期决策规则
- 状态流转规则
- 默认参数规则
- 排序 / 聚合 / 过滤规则
- 幂等 / 去重 / 覆盖规则
- 容错 / 回退规则

再到代码中定位对应实现，核对是否一致。

若文档规则与实现冲突：

- 会误导修改行为 = 🔴
- 只是表述不严谨 = 🟡

### 检查维度 3: 外部依赖契约是否一致

核对文档中提到的：

- 环境变量
- 配置文件
- 数据库
- 表名
- 文件路径
- 第三方服务
- 调度方式

检查这些内容在当前代码和配置中是否仍真实存在。

若文档中记录的依赖已失效、改名或不再使用：

- 仍被当成当前事实陈述 = 🔴
- 属于历史信息但未标历史 = 🟡

### 检查维度 4: 数据契约是否一致

核对：

- 核心表 / 文件 / 接口是否仍存在
- 关键字段名是否仍一致
- 文档中的字段含义、时间口径、主键口径是否仍成立

如果无法从代码稳定验证完整字段语义，可保守标记为：

- 🟡 待人工确认

### 检查维度 5: 模块职责边界是否一致

核对文档是否把职责描述错位，例如：

- 把 orchestration 写成核心算法
- 把适配层写成业务规则来源
- 把已废弃模块当成当前主模块

这种错误对 AI 影响很大，要重点标出。

---

## Phase 5: 低价值文档识别

对 `snapshot`、`supporting`、`noise-candidate` 文档，检查是否属于噪音。

### 低价值信号

- 内容主要是代码复述
- 只有目录树/文件列表，无额外知识
- 和其他文档高度重复
- 标题很大，正文信息量很低
- 已被后续更完整文档覆盖
- 没有任何引用，也没有保留必要性
- 分析报告没有明确标注为历史快照

### 动作建议

对低价值文档只给出这些建议之一：

- `保留`
- `合并`
- `归档`
- `删除候选`
- `重写为更短的核心文档`

---

## Phase 6: 引用、重复、孤立辅助检查

这些检查是辅助项，优先级低于“知识一致性”。

### 1. 引用有效性

只检查明确引用：

- Markdown 链接
- 明确相对路径
- 明确文件路径

判定：

- 本地文件不存在 = 🔴 死引用
- 锚点不存在 = 🟡 锚点失效
- 外部 URL = 仅记录，不做联网校验

### 2. 重复 / 重叠

轻量检查：

- 标题相似
- 一级 / 二级标题高度重叠
- 关键词重叠明显
- 面向同一主题但重复表达

判定：

- 实质重复 = 🔴
- 可合并 = 🟡

### 3. 孤立文档

检查是否被其他文档或索引页引用。

豁免：

- 根 `README`
- `CHANGELOG`
- `LICENSE`
- 明确标记为历史快照的归档文档

零引用不一定是问题，但若同时低价值，则作为删除候选。

---

## Phase 7: 生成审计报告

写入 `docs/docs-audit-report.md`。

报告结构如下：

```markdown
# 文档审计报告

> 生成时间: {datetime}
> 扫描范围: {path}
> 文档总数: {count}

## 摘要

- high-value 文档: {n}
- medium-value 文档: {n}
- low-value / noise 候选: {n}
- 与代码不一致的高风险文档: {n}

## 一、建议保留并持续维护的核心文档

| 文档 | 知识类型 | 保留理由 | 当前状态 |
|------|---------|---------|---------|

## 二、与代码不一致的重点问题

| 文档 | 问题级别 | 问题类型 | 证据 | 建议动作 |
|------|---------|---------|------|---------|

问题类型示例：
- 入口失真
- 流程失真
- 规则失真
- 外部依赖失真
- 数据契约失真
- 模块职责失真

## 三、可合并 / 可归档 / 可删除候选

| 文档 | 当前类别 | 原因 | 建议动作 |
|------|---------|------|---------|

## 四、历史快照文档

| 文档 | 时间信息 | 是否仍有参考价值 | 建议动作 |
|------|---------|----------------|---------|

## 五、死引用 / 重复 / 孤立问题

### 死引用
### 疑似重复
### 孤立文档

## 六、完整清单

| 文档 | 一级类别 | 知识类型 | 保留价值 | 最后修改 | 备注 |
|------|---------|---------|---------|---------|------|
```

无内容的章节直接删除，不保留空表。

---

## 最终输出给用户的摘要

报告完成后，只向用户展示：

1. 文档总数
2. `high-value / medium-value / low-value` 各多少
3. 最值得保留的 3 类核心知识
4. 最严重的 3 个“文档与代码不一致”问题
5. 最应删除/归档的 3 份噪音文档

然后告知完整报告已写入：

`docs/docs-audit-report.md`

---

## 守护栏

- **只读不删**
- **优先做知识审计，不要沉迷格式审计**
- **能从代码直接推断出的信息，默认低价值**
- **对历史快照要区分“过时”和“错误”**
- **拿不准时标 🟡，并写明不确定原因**
- **输出中文**
