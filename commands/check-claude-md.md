逐章检查 **`$ARGUMENTS`** 的 `CLAUDE.md`。

## 定位

CLAUDE.md 是**部署与运行现状的交接快照**，读者是下一个接手的人或 AI。它的价值是让人少踩坑、少误判。

**架构与踩坑不写在这里**——代码结构归 `ARCHITECTURE-*.md`、踩坑归专门文档（如 `docs/pitfalls.md`）。它们不随部署漂移，混进来会两头都过期。但 **§9 文档索引必须指得到它们**，否则等于知识丢失。

⚠️ **不做结构打勾。** 章节齐全但内容与实测不符的 CLAUDE.md 比缺章更危险——它让人放心地照错的做。**每章验收里，"与实测一致"永远是权重最高那条。**

---

## 目录规范（合格的 CLAUDE.md 必须长这样）

```
# CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> 事实截止：YYYY-MM-DD HH:MM（<几台机器 / 什么时刻的实测快照>）
> 本文只记部署与运行现状，会随时间漂移，改动后请同步更新。
> 代码结构见 ARCHITECTURE-*.md，踩坑见 docs/pitfalls.md（详见 §9）

## 0. 程序概览
## 1. 输入
## 2. 输出
## 3. 环境部署信息
## 4. 部署仓库信息
## 5. 日志信息
## 6. 项目配置信息
### 6.1 配置文件
### 6.2 当前关键配置
## 7. 项目启动信息
### 7.1 启动入口
### 7.2 计划任务 / 调度
### 7.3 运维命令
## 8. 通知总表
## 9. 文档索引
```

| 章 | 内容要点 | 性质 | 权重 |
|---|---|---|---|
| 头部 | 事实截止时间 + 漂移声明 + 指向架构/踩坑 | 元信息 | 🔴 缺则全文可信度打折 |
| **0** | 做什么 / 几条链路 / 哪些机器 / 各机职责 / 是否碰数据库 / 分流机制 | 会漂移 | 中 |
| **1** | **输入**：外部 API 端点、账号与凭据位置、文件路径与上游、库表、增量状态 | 会漂移 | 🔺 **最高** |
| **2** | **输出**：去向、下游谁读、是否进生产库、幂等/覆盖语义 | 会漂移 | 🔺 **最高** |
| **3** | OS / 运行时精确版本 / 依赖安装命令 / venv 位置 / 外部软件 / 网络前提 | 会漂移 | 中 |
| **4** | 仓库 URL / 分支口径 / HEAD / 拉码方式与 key 权限范围 / 代码根 | 会漂移 | 中 |
| **5** | 日志路径 / 保留策略 / 排障先看哪个 | 会漂移 | 低 |
| **6** | 配置文件清单 / 必填与可选键 / 当前关键值 / **硬编码魔法值** | 会漂移 | 高 |
| **7** | **启动**：入口与完整命令 / 参数约束 / 退出码 / 调度 / 运维命令 / 真假运行判据 | 会漂移 | 🔺 **最高** |
| **8** | 通知渠道与触发条件 / 投递失败是否改退出码 | 会漂移 | 中 |
| **9** | 文档索引——**必须指得到架构文档与踩坑文档** | 半漂移 | 高 |

**三条结构规则**

1. **编号可以不严格一致，但语义必须一一对应。** 章名叫「运行环境」还是「环境部署信息」不重要，能对上第 3 章的内容要点即可。
2. **不得混入代码架构长篇。** 架构写 `ARCHITECTURE-*.md`、踩坑写专门文档——它们不随部署漂移，混进来会两头都过期。CLAUDE.md 只管**现在这台机器上是什么状况**。
3. **顺序不要乱。** 这个顺序就是接手人的阅读顺序：先知道**这是什么**（§0）→ **喂什么、产出什么**（§1–2）→ **环境和代码从哪来**（§3–4）→ **出问题看哪**（§5）→ **怎么配、怎么跑**（§6–7）→ **谁会收到通知**（§8）→ **还有什么可读**（§9）。

> 📌 §1 / §2 / §7 是权重最高的三章，它们回答"喂什么、产出什么、怎么跑"。这三章任一不合格，整份文档即不可依赖。

## 通用铁律

- **一切实拉**，禁止凭记忆、凭台账、凭上一轮结论
- **禁止打印凭据**：只报「第 N 行有明文 `MYSQL_PASSWORD`」，不回显值
- **不改文档**：只输出问题与补丁建议，落地前先问
- **推测标注"推测"**；拿不到写 `🟡 未取到` + 原因

# 逐章验收条件

## 头部（§0 之前）

**必填**

1. `事实截止：YYYY-MM-DD HH:MM` —— **精确到分钟**，并说明是几台机器 / 什么时刻的快照
2. 声明本文只记**部署与运行现状**、会漂移、改动后需同步
3. 指向架构文档与踩坑文档

**怎么核**

```bash
git -C <repo> log -1 --format='%h %ad %s' --date=iso              # 代码最后提交
git -C <repo> log -1 --format='%h %ad' --date=iso -- CLAUDE.md    # 文档最后改动
```

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 有事实截止（到分钟）+ 漂移声明；截止时间 ≥ 代码最后提交日期 |
| 🟠 | 有截止时间但**早于代码最后提交** → 列出中间改了哪些文件 |
| 🔴 | **无事实截止声明** —— 全文无从判断是否过期，后续所有章节可信度打折 |

---

## §0 程序概览

**必填**

- 程序做什么（一句话）
- 几条链路 / 几个入口，各是什么
- **运行在哪些机器**——逐台点名，不许写"服务器上"
- 各机职责差异（同份代码在不同机器跑不同活时必须说清）
- **是否读写数据库**——「不读不写」也**必须显式写**，留空不算
- 分流机制（哪台跑什么由什么决定：配置？代码判断？）

**怎么核**：文档列的每台机器，验其代码根路径实际存在。

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 能直接答出"在哪几台机器跑、各自干什么、碰不碰数据库" |
| 🟠 | 机器列了但职责差异没说清 |
| 🔴 | 机器名不具体 ／ 数据库一栏留空 ／ 列的机器路径实测不存在 |

---

## §1 输入

**必填**（表格：类型 / 具体输入 / 来源路径或端点 / 各机状态 / 用途）

- 外部 API：给**端点**，不是"调接口"
- 账号与凭据：给**键名 + 所在文件**，不给值
- 文件输入：给**绝对路径** + **上游是谁产出的**
- 数据库输入：给 `实例.库.表`
- 增量状态：状态文件路径 + 语义（水位？去重名单？）
- 命令行参数：指向 §7，此处不重复

**怎么核**：抽 2–3 个路径/表实测存在性；配置键 vs `*.example`（**比键名不比值**）。

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 每行都指向**可验证的位置**（路径/端点/表名）；有"无数据库输入"这类显式否定 |
| 🟠 | 出现"在配置文件里"这种模糊指向；文件输入没写上游是谁 |
| 🔴 | **抽查路径/表实测不存在** ／ 列的输入项已废弃（例：指向已撤下仓库的产出目录） |

---

## §2 输出

**必填**

- 每类输出的**去向**：绝对路径 / `实例.库.表` / bucket 名
- **下游谁读**——没有也要写"无下游"
- **会不会进生产库**（进了必须显式标出）
- **幂等/覆盖语义**：重跑会怎样？按日 `DELETE+INSERT`？原地覆盖？重名加后缀？

**怎么核**：抽一个输出路径/表，验实际有没有产物。

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 写库的写清 schema 与是否生产；下游消费者明确；重跑语义明确 |
| 🟠 | 有输出项没写下游 |
| 🔴 | 只写"写入数据库"不给库表名 ／ **没写覆盖/幂等语义**（重跑行为不可预测） ／ 输出会进生产库却没标出 |

---

## §3 环境部署信息

**必填**

- OS 与版本
- 运行时**精确版本**（`Python 3.11.7` 而非 `3.x`；MATLAB 版本号）
- 依赖安装方式 + **可粘贴执行的命令**
- venv 位置（**可能在子目录**，不一定在仓库根下）
- 外部软件依赖（MATLAB / 券商客户端 / 数据库客户端）
- 网络前提（能否到 PyPI / GitHub / 内网；要不要镜像）

**怎么核**：把文档给的安装命令**实际跑一遍**（至少做到 `--version` / `--help` 级验证）。

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 版本精确到小版本；安装命令实测可执行 |
| 🟠 | 没写网络前提（换机器会卡在拉包） |
| 🔴 | **文档给的命令实测跑不通**。例：`pip install -r requirements.txt` 在 GBK 环境必崩——文件是 UTF-8 带中文注释，pip 按 locale 解码 |

---

## §4 部署仓库信息

**必填**

- 仓库 URL
- **分支口径**：约定该跑哪个分支
- 当前 HEAD（短 sha + 日期）
- **拉码方式**：remote 形式、deploy key 别名、**该 key 的权限范围**（仓库级只读？org 级宽权限？）
- 代码根路径（是否符合统一根约定）

**怎么核**

```bash
git -C <repo> status -sb                 # 分支 + 落后/领先
git -C <repo> remote get-url origin
# ⚠️ remote 写了别名不等于别名存在——必须核 ~/.ssh/config 里真有那个 Host
```

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 分支口径与实际一致；deploy key 别名真实存在且权限范围写对 |
| 🟠 | HEAD 已过期（可接受，但要能看出来） |
| 🔴 | **实际跑在特性/个人分支而文档说主干** ／ **remote 别名在 ssh config 里不存在**（拉不动） ／ 文档说只读实际是 org 级宽权限密钥 ／ 代码根不符合统一约定却未标出 |

---

## §5 日志信息

**必填**

- 日志路径（含 stdout / stderr 分开的情况）
- 切分与**保留策略**
- 出错先看哪个文件
- 计划任务的控制台日志在哪（常与程序日志不是同一个）

**怎么核**：路径实测存在；最近文件时间戳是否与最近一次运行吻合。

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 路径实测存在；说清排障先看哪个 |
| 🟠 | **没写保留策略** → 磁盘增长无人管 |
| 🔴 | 路径实测不存在 |

---

## §6 项目配置信息

**必填**

- **6.1 配置文件清单**：路径 + 作用 + 哪些由模板复制而来
- 必填键与可选键**分开列**
- **6.2 当前关键配置**：非敏感值照实写（路径、库名、机器标识、开关）
- 🔴 **硬编码的魔法值必须点名**——代码里写死、配置里看不见、换环境就静默失败的那些

**怎么核**

```bash
grep -oE '^[A-Za-z_][A-Za-z0-9_]*=' .env.example | sort -u    # 键面比对，只比键名
grep -nEi 'password|passwd|secret|token|webhook|api[_-]?key|accesskey' CLAUDE.md
```

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 键清单与 `*.example` 一致；关键非敏感值照实写；硬编码约定已点名 |
| 🟠 | 缺可选键说明 ／ 机器标识类配置没说各机应填什么 |
| 🔴 | **有明文凭据** ／ 文档列的键与 `*.example` 不符 ／ **存在未点名的硬编码魔法值**。例：代码写死 `market='CN_A'`，而某环境表里是 `SH` → 换库后交易日判断全错、程序静默产出 0 条 |

---

## §7 项目启动信息

**本章验收最严——它直接决定别人能不能把程序跑对。**

**必填**

- **7.1 入口**：唯一业务入口 + **完整可粘贴命令**
- **参数成对 / 互斥约束**
- **退出码语义**（含非 0 非 1 的特殊码）
- 有没有 `--dry-run`；**默认是干跑还是真跑**
- **7.2 计划任务**：任务名 / 路径 / 触发时刻 / 当前状态 / **action 实际指向的路径**
- **7.3 运维命令**：只读查状态怎么查；恢复 / 续跑怎么做
- **"绿色不等于干了活"的判据**：若程序在无输入 / 复用 / 降级时仍返回 0，必须写清怎么区分真跑

**怎么核**

```bash
<入口> --help                      # 文档给的参数签名必须与 --help 一致
schtasks /query /fo table /nh      # 任务名/状态/action 路径 vs 文档
```

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 命令签名与 `--help` 一致；退出码表齐全；参数约束写明；计划任务 action 路径与文档代码根一致 |
| 🟠 | 缺只读查状态命令 ／ 没写默认是 dry-run 还是真跑 |
| 🔴 | **没写退出码语义**（例 `3`=DEGRADED：`if errorlevel 1` 会误当普通失败，人眼又会粗看成成功）<br>🔴 **没写参数成对约束**（例 `--data-date` 缺 `--valuation-date` 直接 `ValueError`）<br>🔴 **文档命令粘贴执行失败**（例文档写 `--resume <run-id>`，实际 `--resume` 是不带值的 flag）<br>🔴 **计划任务 action 指向的路径与文档声明的代码根不一致**（跑的是另一份代码）<br>🔴 程序会"空转成功"却没写判据 |

## §8 通知总表

**必填**

- 渠道（飞书 / 邮件 / 其它）与**触发条件**（成功？失败？两者？）
- webhook 配在哪（**键名**，不给 URL）
- 🔴 **投递失败是否影响主流程退出码**
- 通知里的机器标识来自哪个配置（错了会误导排查方向）

**怎么核**：确认 webhook 键在配置里存在；确认通知与业务执行是否解耦。

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 触发条件明确；**投递与主流程的耦合关系写清** |
| 🟠 | 没说通知里的机器标识来源 |
| 🔴 | **明文 webhook URL** ／ 没写"投递失败不改退出码"这类耦合事实（会造成"日更报 PASS 但没人收到告警"） |

---

## §9 文档索引

**必填**

- 指向**架构文档**（`ARCHITECTURE-*.md` 等）
- 指向**踩坑文档**
- 其它 `docs/` 下关键文档 + 一句话说明各装什么

**怎么核**：**每个链接指向的文件实测存在。**

**验收**

| 判定 | 条件 |
|---|---|
| ✅ | 架构与踩坑文档都指得到，且文件实际存在 |
| 🟠 | 索引存在但没覆盖架构或踩坑 |
| 🔴 | **无 §9** ／ **链接指向的文件不存在**（等于知识丢失） |

## 附加检查：重写有没有丢知识

```bash
git -C <repo> log --oneline -- CLAUDE.md | head -10
git -C <repo> diff <上一版> HEAD -- CLAUDE.md | grep '^-' | head -40
```

看被删的行里有没有硬约束、判据、警告。**关键是区分"迁走"还是"消失"**：

| 情况 | 判定 |
|---|---|
| 迁到专门文档 + §9 索引指得到 | ✅ 正常重构 |
| 迁走但索引没提 | 🟠 事实上找不到，等于丢 |
| 没迁、直接删 | 🔴 知识丢失 |

> **实战教训**：某 CLAUDE.md 从 232 行精简到 166 行，结构更清晰，却删掉了退出码语义表、"PASS 是否为真"的 6 个判据字段名、告警不改退出码的说明、以及"某运维命令会连带删掉 19 张表含 270 万行"的警告。**结构改善，安全性下降。**
