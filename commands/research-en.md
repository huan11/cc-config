围绕用户给定的主题，从英文技术社区检索高质量的观点、方法和经验，整理为结构化表格。

## 参数

- **topic**：调研主题（缺少时询问）

## 核心原则

- **只检索英文资料**，中文资料一律跳过
- **观点优先**：找的是「人的经验和看法」，不是官方文档
- **质量 > 数量**：宁可少收录，不凑数
- **表格呈现**：每个方法/观点必须包含「方法 + 原因 + 来源」

## 第一步：多源并行搜索

不需要确认范围，直接开搜。使用 WebSearch 并行发起多组搜索，覆盖以下来源：

| 优先级 | 来源 | 搜索关键词模式 |
|--------|------|---------------|
| P0 | Hacker News | `<topic> site:news.ycombinator.com` |
| P1 | Reddit | `<topic> site:reddit.com` |
| P2 | DEV Community | `<topic> site:dev.to` |
| P3 | 技术博客 | `<topic> best practices / tips / techniques blog` |
| P4 | GitHub Discussions | `<topic> github discussion / awesome` |
| P5 | Medium / Substack | `<topic> guide / experience site:medium.com OR site:substack.com` |
| P6 | 学术/深度文章 | `<topic> research / analysis / case study` |

**搜索要求：**
- 每个来源至少搜 1 轮，高价值来源搜 2-3 轮（换关键词）
- 并行搜索，不要串行等待
- 对搜索结果中最有价值的 3-5 个页面使用 WebFetch 获取全文
- GitHub 数据用 `gh` 命令获取，禁止编造

## 第二步：提取与筛选

从搜索结果中提取具体的方法、工具、观点，按以下标准筛选：

**保留条件（满足任一即可）：**
- 来自有实战经验的开发者（通读过大型项目源码、维护过开源项目等）
- 有具体可操作的步骤，不是泛泛而谈
- 被社区高度认可（高赞、多次被引用）
- 提供了独特的视角或反直觉的洞察

**排除条件：**
- 纯广告或营销内容
- 没有具体方法只有情绪表达
- 过时信息（> 3 年且领域已变化）

## 第三步：分类整理

将筛选后的方法/观点按主题分类，每类一个表格。

**表格格式：**

```markdown
| 方法 | 具体做法 | 为什么有效 | 来源 |
|------|---------|-----------|------|
| 方法名称 | 1-2 句话说清楚怎么做 | 为什么推荐这个方法（原因/效果） | [来源标题](URL) |
```

**分类原则：**
- 按方法的性质自然分组（如：工具类、流程类、思维类）
- 每类 3-8 个方法为宜
- 分类数量 3-10 个，根据内容多少灵活调整

## 第四步：输出报告

保存到用户指定路径，未指定则保存到当前目录下 `<topic-slug>-en-research.md`。

```markdown
# <Topic> — 英文社区方法论整理

> 调研时间: YYYY-MM-DD
> 数据来源: Hacker News / Reddit / DEV / 技术博客 / GitHub / ...

## 一句话总结

社区的核心共识是什么？用一句话概括。

## 一、<分类名称>

| 方法 | 具体做法 | 为什么有效 | 来源 |
|------|---------|-----------|------|
| ... | ... | ... | [...](url) |

## 二、<分类名称>

（同上格式）

...

## N、总结对比

| 场景 | 推荐方法 | 适合谁 |
|------|---------|--------|
| 场景 A | 方法 X + 方法 Y | 角色 |
| ... | ... | ... |

## Sources

- [Source 1](url)
- [Source 2](url)
- ...
```

## 守护栏

- **只收录英文来源**，中文内容一律跳过
- 禁止编造 URL，搜不到标注"未找到"
- 每个方法必须有「为什么有效」，禁止只列方法不讲原因
- 事实给来源链接，观点标注"社区共识"或引用原文
- 搜不到高质量内容的分类直接跳过，不凑数
- GitHub 数据用 `gh` 实时获取，禁止凭记忆编数字
