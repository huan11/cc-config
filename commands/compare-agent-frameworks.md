横向调研智能体（Agent）开发框架，从多维度进行结构化对比和排名，输出可落地的选型报告。

## 参数

- **scope**（可选）：框架列表或领域关键词
  - 示例 A：`LangChain CrewAI AutoGen` — 指定框架直接对比
  - 示例 B：`Python Agent框架` — 先搜索再筛选 Top 框架
  - 不提供则自动搜索当前主流 Top 5-8 框架，无约束全面调研

## 第一步：搜索候选框架

直接开始搜索，不向用户确认范围。默认参数：
- 场景：通用 Agent 开发（不限定单/多 Agent、RAG、工具调用等）
- 语言：不限（Python/TS/Java/Go 等均纳入）
- 关注点：均衡，8 个维度等权看待
- 数量：搜索当前主流 Top 5-8 框架

如果用户通过 scope 参数指定了框架列表，则跳过搜索直接进入信息采集。

搜索方式：
- WebSearch 搜索 "best AI agent frameworks 2026"、"top agent development frameworks comparison" 等关键词
- 结合 GitHub trending、社区讨论筛选出候选列表
- 确保覆盖不同定位的框架（轻量 vs 全功能、单 Agent vs 多 Agent、代码优先 vs 低代码）

## 第二步：信息采集

对每个框架，按优先级采集信息：

| 优先级 | 来源 | 获取方式 | 采集内容 |
|--------|------|---------|---------|
| P0 | 官方文档 | WebSearch → WebFetch | 核心概念、架构设计、API 风格 |
| P1 | GitHub 仓库 | `gh` 命令实时获取 | Stars、Forks、最近提交、Issue 数、Contributors |
| P2 | PyPI / npm | WebSearch | 下载量、版本发布频率 |
| P3 | 社区评价 | WebSearch | 真实用户反馈、踩坑经验 |
| P4 | 基准测试 | WebSearch | 性能对比（如有） |

**数据纪律：**
- GitHub 数据必须用 `gh` 实时获取，禁止凭记忆编数字
- 找不到的数据标注"未找到"，不凑数
- 社区评价标注来源，区分"官方宣称"和"用户反馈"

## 第三步：多维度评分

### 评分维度（每项 0-100 分）

| 维度 | 权重 | 评分标准 |
|------|:----:|---------|
| **上手门槛** | 15% | 文档质量、学习曲线、示例丰富度、概念复杂度 |
| **架构设计** | 15% | 抽象合理性、模块化程度、设计哲学清晰度 |
| **功能完备性** | 15% | 工具调用、记忆管理、多模型支持、多 Agent、流式输出、Human-in-the-loop |
| **生态与集成** | 10% | 内置工具/连接器数量、第三方集成、社区插件 |
| **生产可用性** | 15% | 可观测性、错误处理、重试机制、部署支持、类型安全 |
| **社区活跃度** | 10% | GitHub 活跃度、Issue 响应速度、版本迭代频率、社区规模 |
| **性能与效率** | 10% | Token 消耗效率、延迟、并发处理、资源占用 |
| **可扩展性** | 10% | 自定义组件难度、架构灵活性、escape hatch 质量 |

### 评分规则

- **S 级 (90-100)**：行业标杆，几乎无短板
- **A 级 (75-89)**：优秀，有明显优势
- **B 级 (60-74)**：合格，能用但有明显不足
- **C 级 (40-59)**：勉强，有较大缺陷
- **D 级 (0-39)**：不推荐，存在严重问题

每个评分必须附带一句话理由，禁止"感觉差不多"这种模糊评价。

## 第五步：场景化推荐

报告输出后，给出最终推荐：

1. **最佳选择**：综合最优，附理由
2. **备选方案**：第二选择，说明什么情况下反而更优
3. **下一步建议**：推荐做哪些 PoC 验证

## 守护栏

- GitHub Stars/Forks 等数据必须用 `gh` 实时获取，禁止凭记忆编造
- 禁止编造 URL，搜不到标注"未找到"
- 每个评分必须有依据，不允许"差不多"这种模糊评价
- 事实给来源，观点标注"社区观点"或"个人判断"
- 区分"官方宣称"和"实际体验"
- 对比必须公平，不预设立场偏向任何框架
- 承认自己知识截止日期，标注哪些信息可能已过时
