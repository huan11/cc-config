深度分析一个模块的设计、依赖关系和上下游，评估将其独立拆分的可行性与工作量。

## 参数

- **module**：模块路径或名称（缺少时询问）

## 第一步：确认模块边界

先问用户确认，不要直接扫：

1. **模块位置**：具体的目录路径或入口文件
2. **当前职责**：这个模块大概负责什么（用户口述即可，后面会验证）
3. **拆分意图**：想独立成 SDK / 微服务 / 独立仓库 / npm 包？不同目标影响分析侧重点

用户说"你看着办"则按独立仓库处理。

## 第二步：模块自身分析

### 2.1 结构扫描

- 目录结构（用 tree 或 glob 扫描）
- 文件数量、代码行数统计
- 入口文件 / 导出接口识别
- 内部分层（如 controller / service / model / util）

### 2.2 职责分析

- 这个模块实际做了哪些事？列出核心职责
- 是否存在职责越界（做了不该它做的事）？
- 是否存在隐式职责（看起来没做但删了会挂的）？

## 第三步：依赖分析

### 3.1 外部依赖（第三方库）

扫描 import / require / 配置文件，列出：

| 包名 | 用途 | 是否可替换 | 备注 |
|------|------|-----------|------|

### 3.2 内部依赖（依赖项目其他模块）

扫描模块内所有跨模块引用，列出：

| 被依赖模块 | 引用位置 | 引用内容 | 耦合程度 |
|-----------|---------|---------|---------|

耦合程度判定：
- **轻**：只用了工具函数或常量
- **中**：用了类型定义、接口、配置
- **重**：直接调用了业务逻辑、共享了可变状态

### 3.3 上游（谁依赖我）

扫描整个项目，找出所有引用当前模块的地方：

| 上游模块 | 引用位置 | 引用内容 | 影响程度 |
|---------|---------|---------|---------|

影响程度 = 如果当前模块被拆走，上游需要改多少。

### 3.4 下游（我依赖谁）

和 3.2 相同视角，但侧重"如果拆走，这些依赖怎么带走或替换"。

### 3.5 隐式依赖

不在代码 import 中，但实际存在的依赖：

- 共享数据库表
- 共享配置文件 / 环境变量
- 共享中间件 / 拦截器
- 事件总线 / 消息队列
- 文件系统路径约定
- 运行时全局变量 / 单例

## 第四步：依赖关系图

用 Mermaid 画一张依赖关系图：

```
graph LR
  上游A --> 当前模块
  上游B --> 当前模块
  当前模块 --> 下游C
  当前模块 --> 下游D
  当前模块 -.-> 隐式依赖E
```

实线 = 显式 import，虚线 = 隐式依赖。

## 第五步：独立拆分评估

### 5.1 拆分可行性评分

从 5 个维度打分（1-5 分，5 = 最容易拆）：

| 维度 | 得分 | 说明 |
|------|------|------|
| 接口清晰度 | ? | 对外暴露的接口是否明确、稳定 |
| 内聚性 | ? | 模块内部是否围绕单一职责 |
| 耦合度 | ? | 与其他模块的纠缠程度 |
| 数据独立性 | ? | 是否有独立的数据边界 |
| 可测试性 | ? | 能否独立运行测试 |
| **综合** | ? | 加权平均 |

### 5.2 需要做的工作

按阶段列出拆分所需的具体工作：

**阶段一：解耦准备**
- [ ] 需要处理的耦合点（逐条列出）
- [ ] 需要抽象的接口
- [ ] 需要拆分的共享代码

**阶段二：独立化**
- [ ] 独立的构建配置
- [ ] 独立的依赖管理
- [ ] 独立的测试套件
- [ ] 独立的配置管理

**阶段三：集成方案**
- [ ] 原项目如何引用拆分后的模块（npm 包 / git submodule / API 调用）
- [ ] 版本管理策略
- [ ] 发布流程

### 5.3 风险点

| 风险 | 影响 | 缓解方案 |
|------|------|---------|

### 5.4 建议

给出明确建议：**建议拆** / **暂不建议拆** / **建议先做 XX 再拆**，并说明理由。

## 输出格式

保存到 `docs/module-audit/<module-slug>.md`（目录不存在则创建）。

## 守护栏

- 依赖关系必须从代码扫描得出，禁止凭印象猜测
- 隐式依赖扫不出来的，如实标注"需人工确认"
- 耦合程度、影响程度的判定要给出依据，不要拍脑袋
- 拆分工作量不给时间估算，只列工作项
- 发现模块本身设计有问题的，如实指出，不回避
