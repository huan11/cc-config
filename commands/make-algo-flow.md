对指定的函数、模块或算法绘制详细的 ASCII 流程图，展示所有分支、判断条件和边界处理。

目标: $ARGUMENTS

用户可能传入以下几种格式：
- 文件+函数: `file.py:function_name`
- 函数名: `compute_weights`
- 自然语言描述: `数据清洗模块`、`权重计算逻辑`

如果用户只给了模糊描述，自行搜索代码库定位到具体文件和函数，不要反问用户要文件路径。如果确实无法定位（比如描述太模糊且搜索无结果），再询问用户补充信息。

## 命令族导航

1. `/make-repo-card` — 这是什么
2. `/make-repo-behaviors` — 做了什么、遵循什么规则
3. `/make-exec-flow` — 怎么跑起来的（宏观执行流）
4. **`/make-algo-flow`** ← 当前：具体怎么算的（微观算法流程）

和 `/make-exec-flow` 互补：exec-flow 画宏观主干（从入口到输出的层级），algo-flow 钻进某个节点画微观细节（所有分支和判断）。

## 产出物

`docs/algo-flow-[名称].md` — 算法流程图文档（名称取自函数名或模块名）

## 核心概念

算法流程图关注的是**一个具体算法/函数内部的完整决策树**：
- 每个 `if/else`、`switch`、`try/catch` 都是一个分支节点
- 每个分支标注**为什么走这条路**（设计意图），不只是写条件表达式
- 边界情况和异常路径和正常路径同等重要

目的是让人理解：这段代码考虑了哪些情况，每个判断的意图是什么，有没有遗漏。

## 执行流程

### Phase 1: 定位目标代码

1. 根据参数定位到具体的函数或代码段
2. 通读目标代码，理解整体逻辑
3. 如果函数调用了其他关键子函数，判断是否需要展开 — 只展开对理解核心逻辑必要的子函数，其他标注为"调用 xxx"即可，避免无限递归导致图变得不可读

### Phase 2: 识别所有分支

逐行扫描目标代码，标记所有决策点：条件分支、循环、异常处理、提前返回等。

每个决策点记录：
- 条件表达式（代码原文）
- 设计意图（为什么要做这个判断 — 这是流程图比直接读代码更有价值的地方，因为条件代码里写了，意图代码里通常没写）
- 各分支去向

### Phase 3: 绘制流程图

按以下格式绘制 ASCII 流程图，写入 `docs/algo-flow-[名称].md`：

### Phase 4: 展示确认

产出完成后，展示：

- **功能概述**: 一句话
- **流程图**: 直接展示 ASCII 图
- **复杂度摘要**: N 个决策点、M 个边界情况

等待用户确认。

## 绘图规则

- **矩形** `┌──┐` 表示处理步骤
- **菱形** `╱╲` 表示判断/决策
- **箭头** `│ ▼ →` 表示流向
- 每个决策点旁标注**意图**
- 每个步骤旁标注 `file.py:line`
- 分支汇合时画清楚汇合点

## 守护栏

- **深读一个点** — 和 `/make-exec-flow` 相反，这里要逐行分析，不遗漏分支。这是本命令的核心价值。
- **意图比条件重要** — 每个判断必须标注设计意图。条件表达式代码里已经有了，意图才是流程图比直接读代码更有价值的地方。
- **子函数适度展开** — 只展开理解核心逻辑必要的子函数。展开太多会让图变成调用树，失去"一个算法的决策全景"这个核心价值。
- **诚实标注疑问** — 逻辑不清楚的放到"待确认项"。强行解释一段看不懂的代码，比留白危害更大。
- **目标仓库只读** — 只写 `docs/algo-flow-[名称].md`，不修改任何已有文件。
