基于 `docs/scan-manifest.md` 的文件分类，逐文件精读代码，提取业务规则证据，组织为三层文档。

## 前置条件

`docs/scan-manifest.md` 必须存在且已经用户确认。如果不存在，提示用户先运行 `/biz:scan`。

## 输入参数

- `--module <name>`: 只提取指定模块的文件（按 scan-manifest 中的模块列匹配）。不指定则全量提取。

## 基本原则

1. **逐文件，不跳过** — scan-manifest 中的 ACTIVE_CORE 和 LEGACY_CORE 必须完整阅读
2. **提取，不编造** — 规则来自代码事实；解释可以有，但必须追溯回代码
3. **三层分离** — 说明书讲业务，底稿讲证据，矩阵讲映射
4. **主链优先，遗留隔离** — 当前生效规则进说明书，遗留只进底稿
5. **编号稳定** — 已有 BR-XX 和 INV-XXXX 保留，新增追加，废弃标记不回收
6. **代码优先** — 文档间冲突时以源码为准

## Phase 1: 逐文件精读 → 取证底稿

对 scan-manifest 中的文件，按状态处理：

| 文件状态 | 处理方式 |
|---------|---------|
| ACTIVE_CORE | 完整阅读，逐行提取证据 |
| LEGACY_CORE | 完整阅读，证据归入遗留区 |
| SUPPORTING_BUSINESS | 检查，有规则则提取，无规则标"已检查，无独立业务规则" |

### 证据提取对象

| 提取对象 | 成为证据的条件 |
|---------|--------------|
| 条件分支 | 基于业务条件进入不同路径 |
| 计算公式 | 影响业务结果的数值运算 |
| 数据过滤 | 保留、排除、归类、分层 |
| 校验规则 | 抛错、告警、阻断条件 |
| 常量阈值 | 业务阈值、白名单、黑名单、窗口 |
| 数据源选择 | 根据条件读取不同表/文件/接口 |
| 输出定义 | 输出表、输出列、枚举映射、文件格式 |
| 执行顺序 | 先后依赖、串行/并行关系 |
| 特殊处理 | 硬编码覆盖、例外路径、补丁逻辑 |

### 每个文件的证据格式

```markdown
## 文件: Tracking/running_main.py

文件状态: ACTIVE_CORE
文件角色: Tracking 模块主循环与时段控制

| # | 行号 | 代码事实 | 规则解释 | 分类 | 主链状态 |
|---|------|---------|---------|------|---------|
| 1 | 55-60 | `hour==9 and minute<35` 下清空多张 `realtime_*` 表 | 开盘前 9:00-9:34 清空实时结果表 | 时段控制 | current |
| 2 | 65-67 | `hour >= 16` 调用 `historySql_saving` | 收盘后归档 realtime 数据为历史数据 | 收盘处理 | current |
```

### 底稿末尾独立 section

- 遗留/非主链代码说明
- 已知问题与潜在 Bug
- 排除文件说明
- 缺失上下文与外部依赖

## Phase 2: 按业务域组织 → 业务说明书

从证据中把 ACTIVE_CORE 的规则按业务域整合。目标不是"逐文件展示"，而是"按业务域解释当前系统如何工作"。

### 说明书约束

- 只写当前生效规则
- 遗留逻辑、死代码不进正文
- 每条规则必须有 evidence 支撑
- 同一业务域内规则不互相矛盾
- 同一规则不在多个 BR 中重复

### BR section 模板

```markdown
## BR-07: Tracking 实时初始化

目的:
- 在开盘前清空上一轮实时结果，保证当日实时计算从干净状态开始

### BR-07a: 开盘前清空实时表

触发条件:
- 当前时间满足 `hour == 9` 且 `minute < 35`

处理规则:
1. 系统进入开盘前初始化窗口
2. 清空以下实时表：realtime_portfolioreturn、realtime_scoresplit 等 7 张表

边界与例外:
- 9:35 及以后不再执行该清理逻辑

来源:
- Tracking/running_main.py:55-60
```

**模板规则：**
- **"目的"必填** — 每个 BR 开头说明解决什么业务问题
- 子规则的"触发条件/输入/处理规则/边界与例外/输出"按需使用
- **"来源"始终压到末尾**，不在规则描述中穿插行号
- 公式配例子时区分 `例(源码)` / `例(说明性)`

### 说明书结构

```markdown
# [系统名称] 业务规则说明书

> 最后更新: YYYY-MM-DD
> 取证底稿: [business-rules-evidence.md](business-rules-evidence.md)
> 追溯矩阵: [br-inventory.md](br-inventory.md)

## 系统概览
[系统目标、核心模块、日常执行时序]

## BR-01: ...
## BR-02: ...

## 附录 A: 数据依赖汇总
## 附录 B: 常量与阈值
## 附录 C: 缺失上下文说明
```

## Phase 3: 生成追溯矩阵

从 Phase 1 每条证据生成一条 INV 记录。

### INV 状态

| 状态 | 含义 |
|------|------|
| `mapped-active` | 已映射到当前生效 BR |
| `mapped-legacy` | 已映射到遗留说明 |
| `intentionally-unmapped` | 确认不应进入 BR |
| `pending-review` | 暂未确认，需人工回查 |

### 矩阵模板

```markdown
# BR Inventory 追溯矩阵

> 生成时间: YYYY-MM-DD

| INV ID | 来源文件:行号 | 规则摘要 | 映射目标 | 状态 |
|--------|-------------|---------|---------|------|
| INV-0001 | running_main.py:55-60 | 开盘前清空 realtime 表 | BR-07a | mapped-active |

## 覆盖率统计
| 维度 | 数量 |
|------|------|
| 证据总数 | N |
| mapped-active | A |
| mapped-legacy | B |
| intentionally-unmapped | C |
| pending-review | D |
```

## Phase 4: 归档旧版 → 写入

**归档（如 `docs/` 下已有同名文件）：**
1. 复制到 `docs/archive/`
2. 文件名加时间戳：`business-rules_2026-03-14_1830.md`
3. 归档后写入新文件

**写入三个文件：**
1. `docs/business-rules.md`
2. `docs/business-rules-evidence.md`
3. `docs/br-inventory.md`

三份文件之间必须互相链接。

## `--module` 模式补充

指定模块时：
- 只读取该模块的文件
- 证据追加到已有底稿（不覆盖其他模块的证据）
- 说明书中只更新该模块相关的 BR section
- 矩阵中只追加该模块的 INV 记录
- 不归档旧版（增量更新，非全量替换）

## 守护栏

- **不跳文件** — ACTIVE_CORE 和 LEGACY_CORE 必须完整阅读
- **不编造** — 只提取代码中实际存在的逻辑
- **不混层** — 说明书讲业务，底稿讲证据，矩阵讲映射
- **不伪装遗留** — 遗留不进说明书，当前不误归遗留
- **不脑补缺失** — 外部依赖只记录消费方式，不臆造内容
- **不重排编号** — 已有编号只增不删不改
- **不确定就问** — 判断不了的暂停询问用户
