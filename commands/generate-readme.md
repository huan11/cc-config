为当前项目生成或重写 README.md，用可视化方式呈现项目全貌，让人一眼看懂。

## 生成流程

### 1. 理解项目

扫描整个项目，收集以下信息：
- 语言、框架、包管理器（package.json / pyproject.toml / go.mod 等）
- 目录结构和各目录职责
- 入口文件、核心模块、配置文件
- 依赖服务（数据库、缓存、消息队列等）
- 已有文档（CLAUDE.md、docs/、注释等）
- CI/CD、Docker、部署相关配置

如果关键信息无法从代码推断，询问用户。

### 2. 生成 README

严格按以下结构输出，每个章节都要考虑是否需要可视化：

```markdown
# 项目名称

一句话说明这个项目做什么。

## 架构总览

[ASCII 架构图 — 必须有]

## 技术栈

[表格或列表]

## 目录结构

[树形结构 + 关键目录说明]

## 快速开始

[从零到跑起来的最少步骤]

## 配置说明

[环境变量、配置文件说明]

## 开发指南

[日常开发需要知道的事]

## 部署

[如何部署到生产环境，如有]
```

章节不是必须全有，项目用不到的就不写。但**架构总览**和**快速开始**必须有。

### 3. 展示并确认

把生成的 README 完整展示给用户，询问是否需要调整。确认后再写入文件。

## 可视化要求

大量使用 ASCII 图来辅助表达，一张好图胜过多段文字。README 是项目的门面，必须让人一眼看懂架构。

**适用场景：**
- 架构总览（必须有图）
- 数据流向
- 模块依赖关系
- 请求处理流程
- 部署拓扑

**绘图字符：**
```
边框：┌ ─ ┐ │ └ ┘ ├ ┤ ┬ ┴ ┼
箭头：▶ ▼ → ← ──▶
分隔线：═══════════
标记：✓ ✗
```

**绘图原则：**
- 框内只放关键词，不写长句
- 严格对齐，用空格控制列宽
- 先画大标题框，再展开内部细节
- 层级从上到下、从左到右
- 图后紧跟一句总结说明

**示例 — 架构图：**

```
┌─────────────────────────────────────────────────┐
│                   SYSTEM OVERVIEW                │
└─────────────────────────────────────────────────┘

  Client            API Gateway            Services
    │                   │                     │
    ▼                   ▼                     ▼
┌────────┐        ┌──────────┐        ┌─────────────┐
│  Web   │───────▶│  Nginx   │───────▶│  FastAPI     │
│  App   │        │  :443    │        │  :8000       │
└────────┘        └──────────┘        └──────┬──────┘
                                             │
                       ┌─────────────────────┼──────────┐
                       ▼                     ▼          ▼
                 ┌──────────┐         ┌──────────┐ ┌────────┐
                 │  MySQL   │         │  Redis   │ │  OSS   │
                 │  :3306   │         │  :6379   │ │        │
                 └──────────┘         └──────────┘ └────────┘
```

**示例 — 数据流：**

```
  用户请求                    处理流程                   存储
  ═══════                    ════════                   ════

  POST /api/data  ──▶  验证 ──▶ 解析 ──▶ 转换  ──▶  MySQL
                        │                   │
                        ▼                   ▼
                     400 错误            写入日志
```

**示例 — 模块关系：**

```
┌──────────────────────────────────────┐
│              Application             │
├──────────┬──────────┬────────────────┤
│  Routes  │ Services │    Models      │
│  (/api)  │ (业务)   │   (ORM)       │
├──────────┴──────────┴────────────────┤
│           Infrastructure             │
│    DB  │  Cache  │  Config  │  Log   │
└──────────────────────────────────────┘
```

## 写作风格

- 简洁直接，不写废话套话
- 用表格代替长段落
- 命令用代码块包裹，可以直接复制执行
- 中文项目用中文写，英文项目用英文写，跟随项目语言
- 不写"本项目是一个优秀的..."之类的自夸

## 守护栏

- 不编造项目没有的功能
- 不确定的信息询问用户
- 架构图必须反映真实代码结构，不画理想状态
- 生成后必须展示给用户确认，不直接覆盖已有 README
