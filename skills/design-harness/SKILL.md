# design-harness — 把手上的资料变成一个标准 Harness 仓库

> **定位**:用户提供资料,我做专业操作。交付物是**一个能直接跑的文件夹**,不是一份方法论讲解。
> 不要向用户复述"什么是双层循环""什么是四子系统"——那是我的作业依据(见 `references/`),
> 用户只需要看到:料齐不齐、缺什么、以及最后长出来的仓库。

## 铁律

1. **仓库即规范**——不在仓库里的信息对 Agent 等于不存在。对话里达成的共识当场写进文件。
2. **每段做完就 git commit**——不攒到最后。用户看得到进展,也能回滚。
3. **入口文件只做说明**——`AGENTS.md` 控制在 50–200 行,细节进 `docs/`、`skills/`,走到哪读哪。
4. **确定性的归脚本,推断性的归模型**——别让 Agent 数条目、比阈值、算日期。目标:脚本兜住 60–70% 可形式化的检查。
5. **Agent 不得自行宣布完成**——完成与否由脚本判定(见第五段)。
6. **先收料,后设计**——跳过 Step 0 必然返工。

---

## Step 0 — 收料(先别动手设计)

一次性把清单给用户,让他一口气倒完,**避免来回挤牙膏**。原话可以是:
"你手上现成的东西全给我,别整理,散的也行。"

| # | 要什么 | 为什么要(落到哪一段) |
|---|---|---|
| 1 | **现有文档**:需求、方案、会议记录、聊天记录导出、旧的提示词 / AGENTS.md | 二、三段:目标、任务、约束的原料 |
| 2 | **现有代码与脚本**:在哪台机器上、哪些能跑、哪些是半成品 | 一、五段:确定性任务和定时任务的现成家底 |
| 3 | **环境与账号**:服务器清单(SSH/端口)、数据库(实例/库名/凭据位置)、第三方平台(飞书/GitHub/云)、权限边界 | 四段:环境接入清单 |
| 4 | **数据与产物**:输入从哪来、输出写到哪(库表/文件/接口) | 六段:状态台账;也决定要不要建数据血缘 |
| 5 | **只在你脑子里的约定**——问法:"如果新人接手,最容易做错的三件事是什么?" | 三段:constitution.md 的红线和规则 |
| 6 | **你已经纠正过 Agent 两次以上的事** | 三段:每条都是一条该固化的规则 |
| 7 | **目标与验收**:什么算做完、什么节奏检查、看哪个数 | 二段:验收条件;五段:验证脚本 |
| 8 | **例行工作**:每天/每周/每月必须发生的事 | 一、五段:定时任务 |

收完先输出两张表,**别急着写文件**:

- **资料清单**——拿到了什么、覆盖了上面哪几项、各自可信度(现行/过时/待确认)。
- **缺口清单**——缺什么、缺了会导致哪一段做不下去。**只对阻塞项停下来问**,
  非阻塞的按合理默认往下做,并在文件里标 `TODO(待确认)`。

> 卡点:第 7 项(验收条件)拿不到就不许往下走——它是第二段和第五段的唯一依据。
> 用户答不出时,用 `references/smells.md` 第 1 节的三步追问法逼出来,而不是自己替他编。

## 六段落地

每段:**输入什么料 → 我做什么 → 产出哪些文件 → 卡点**。做完一段 commit 一次。

### 一、目录骨架

**输入**:资料清单(知道会有多少脚本、多少外部源,决定要不要建对应目录)

**动作**:`git init` + 按标准结构建骨架 + 写 `.gitignore` + 首个 commit。
只建**这个 harness 真用得上**的目录,空目录不要留。

```
<harness>/
├── AGENTS.md              ← 入口:角色 + 目标 + 任务 + 验收 + 优先级 + 指路
├── CLAUDE.md              ← 软链 → AGENTS.md(Claude Code 读这个名字)
├── docs/
│   ├── constitution.md    ← 红线 / 规则 / 建议,每条带 Rationale
│   ├── decisions/         ← ADR:模块级权衡(上下文-决策-权衡-影响)
│   ├── SOURCE.md          ← 外部知识依赖:哪份文档来自哪、多久同步一次
│   ├── environment.md     ← 环境接入清单:机器/库/平台 + 接入方式 + 凭据位置
│   └── glossary.md        ← 业务词汇(业务型 harness 基本必需)
├── skills/<name>/SKILL.md ← 每个可复用子任务一个技能
├── scripts/
│   ├── check_*.py         ← 验证器:只读数值,输出 PASS/FAIL
│   ├── <task>.py          ← 确定性任务
│   └── cron/              ← 定时任务 + crontab.txt(或 launchd plist)+ 日志约定
├── plans/                 ← 下发的计划(按周/按批)
├── state/
│   ├── STATUS.md          ← 水位线:现在到哪了
│   ├── TODO.md            ← 待办台账
│   └── <task>/progress.json ← 机器可读进度(只记原始数据)
├── requirements.txt
└── setup.sh               ← 新机器 clone 后跑这个就能用
```

**产出**:可 clone 的空骨架 + `.gitignore` + 首个 commit。
**命名**:入口统一 `AGENTS.md`(生态默认名),再软链一个 `CLAUDE.md`;
用户已有 `Agent.md` 之类的就重命名过来,别并存两份入口。
**卡点**:目录怎么切不唯一,但**切完必须在 AGENTS.md 里逐行说明谁读谁写**,否则等于没切。

### 二、指令系统之一:需求明确与定位

**输入**:料 1、7

**动作**:把散在文档和对话里的东西,压成 `AGENTS.md` 的四块:

| 块 | 写什么 | 反面 |
|---|---|---|
| **角色定位** | 你是谁、职责边界、**明确不做什么**(哪些决策必须回来问人) | "你是一个助手" |
| **目标管理** | 北极星目标 + 拆到可执行的子目标;每个子目标挂验收指标 | "把数字化平台建好" |
| **任务管理** | 任务清单 + 每个任务的输入/输出/责任边界;状态指向 `state/TODO.md` | 一堆动词堆在一起,没有先后和依赖 |
| **验收条件** | 可用**是/否**判定的量化条件 + 谁来判(脚本 or 人) | "感觉差不多了""写得很好" |

再单独起一节 **边界情况**(那些"如果……就……"),不要和常规约束混写——
混在一起 Agent 会把边界当主流程跑。

**产出**:`AGENTS.md`(第一版,可先留 `TODO(待确认)`)
**卡点**:验收条件不可量化 → 回 Step 0 第 7 项。不许用"高质量""合理"这类词收尾。

### 三、指令系统之二:业务知识管理

**输入**:料 1、5、6

**动作**分两条线:

**A. 沉规则 → `docs/constitution.md`**
按三档写,**每条必须带 Rationale**(为什么。没有为什么的规则,以后没人敢删也没人会遵守):
- **红线(不可协商)**:安全合规、数据保护、法律要求。用户当面要求也不能破。
- **规则(通常遵守)**:项目级约定,用户明确要求时可覆盖。
- **建议(灵活处理)**:通用最佳实践,冲突时让步。

带历史包袱的模块级权衡(为什么 A 走中介层、为什么 B 还在用旧接口)→ 写成 `docs/decisions/adr-NNN-*.md`。
业务词汇 → `docs/glossary.md`。

在 AGENTS.md 里写死**优先级**,这是以后一切矛盾的裁决依据:
> 红线 > 用户当面指令 > 项目级规则 > 模块级 ADR > 最佳实践

**B. 管外部知识 → `docs/SOURCE.md`**
凡内容来自仓库之外(飞书文档/多维表格、Wiki、Notion、会议决议、第三方接口文档、上游代码库),
登记「仓库文件 → 外部来源 → 更新时机 → 同步方式」。然后按源的性质配机制:

| 源的性质 | 机制 |
|---|---|
| 有 URL / API | 建 `skills/sync-sources/`:读 SOURCE.md → 拉取 → 与本地 diff → 有差异则更新并提 PR;进 `scripts/cron/` 定时跑 |
| 没有固定来源(靠人维护) | 在 AGENTS.md 加会话开场提醒:"先问用户 <X> 有没有更新" |
| 源多且杂(≥5 个平台) | 评估上 OpenWiki 这类带连接器的本地知识库,替代手写 SOURCE.md + 定时技能 |

**产出**:`docs/constitution.md`、`docs/decisions/`、`docs/SOURCE.md`、(可选)`glossary.md`、`skills/sync-sources/`
**卡点**:**过时的文档比没有文档更危险**——Agent 会自信地精准实现一个错误目标。
每份进仓库的外部知识都必须在 SOURCE.md 里有一行,没有更新机制的知识不许进 docs/。

### 四、环境系统

**输入**:料 3

**动作**:列全 Agent 要碰的外部环境,**每一项定一个接入方式**,写进 `docs/environment.md`:

| 环境类型 | 例子 | 接入方式怎么选 |
|---|---|---|
| 服务器 | 生产/测试机、GPU 机 | **CLI 优先**(`ssh`、`gh`、`mysql`):确定、可脚本化、留痕在 shell 历史 |
| 数据库 | 内网/外网 MySQL | CLI 客户端 + 只读账号优先;跨库对账类任务写成 `scripts/` |
| 第三方平台 | 飞书多维表格、GitHub、云控制台 | 有官方 **MCP** 就用 MCP(省去自己封 API);否则 CLI + SDK |
| 浏览器 | 需登录态的页面、看真实渲染效果 | 浏览器自动化 MCP;要用户真实登录态的用本地 daemon 方案 |
| 工作屏幕 | 看 GUI、截图确认 | 截图 / 屏幕控制 MCP,只在 CLI 拿不到时才上 |

每项记四件事:**怎么连(命令或 MCP 名)、连去干什么、权限边界(只读?哪个 org?哪几个库?)、凭据放哪**。

**可复现**:依赖锁进 `requirements.txt`,`setup.sh` 做到"新机器 clone + 跑一条命令就能用"。
环境漂移会让反馈信号失真——用得好好的 Agent 无端变差,先查这里,别只怀疑提示词和模型。

**凭据**:按用户自己的仓库标准处理(要求"运行所需一切入 git"就入,但**必须是私有仓库**);
否则凭据留在机器上,`environment.md` 里只写路径。这一条要跟用户确认一次,别默认。

**产出**:`docs/environment.md`、`requirements.txt`、`setup.sh`、必要的 MCP 配置(配置本身也要入库)
**卡点**:能用 CLI 就别上 MCP、能用 MCP 就别上浏览器、能用浏览器就别上屏幕控制——
越往后越慢越飘。每一次"升级接入方式"都要说得出理由。

### 五、技能与工具系统

**输入**:料 2、7、8

**动作**:把活儿分三类,分别落地:

**A. 可复用的子任务 → `skills/<name>/SKILL.md`**
判据:**这件事会以相同流程重复发生**。一个技能一个操控循环,正文四段写死:
`Guides`(动手前读什么、什么条件才开工)、`Action`(做什么)、`Sensors`(拿什么标准自检)、`Steering`(不达标怎么办、状态写回哪)。
> 技能只负责执行,**不负责计划调整**。计划调整属于 AGENTS.md。
> 若发现每个技能里都抄了一份评分标准/调整规则 → 已腐化,收回入口文件。

**B. 确定性任务 → `scripts/`**
凡"同样输入永远同样输出"的一律进脚本:计数、阈值比较、日期与间隔计算、格式校验、对账、拉数据。
**其中必有一个验证器** `scripts/check_*.py`:只读 `state/` 里的数值字段,
**不解析任何对话内容或 LLM 生成的描述**,输出 `PASS` / `FAIL + 哪个指标 + 当前值`。
然后在 AGENTS.md 里钉上职责边界:
> 你负责执行并在 state/ 记录进度。完成判断由 `scripts/check_*.py` 决定。
> 禁止自行宣布完成;FAIL 时按脚本指出的指标继续做,直到 PASS。

**C. 例行工作 → `scripts/cron/`**
每条定时任务登记:**什么时候跑、跑什么、日志写哪、失败怎么通知**(有飞书/邮件通道就接上)。
`crontab.txt` 或 launchd plist 一并入库,别只存在某台机器的 crontab 里。

**不会写代码不影响**:用自然语言下单——"输入是什么、要判断什么、输出什么格式,
并为调用它的 Skill 生成使用说明,同时生成 requirements.txt 和 setup.sh"。

**产出**:`skills/*/SKILL.md`、`scripts/*.py`、`scripts/cron/*`
**卡点**:验证器缺失 = 白搭。没有它,Agent 做完一半就会宣布完成,而且报得很漂亮。

### 六、状态系统

**输入**:料 4 + 前五段产生的一切

**动作**:建三层状态,分别给人和机器看:

| 文件 | 给谁看 | 写什么 |
|---|---|---|
| `state/STATUS.md` | 人 | **水位线**:系统现在处于什么水平、已具备哪些能力、当前正在做什么、下一个里程碑 |
| `state/TODO.md` | 人 + Agent | **待办台账**:任务、状态(待办/进行中/阻塞/完成)、负责人、依赖、卡在哪 |
| `state/<task>/progress.json` | 机器 | **原始数据**:处理了多少、跳过了哪些及原因、各项指标当前值 |

铁规矩:**只记原始数据,不记自我评价**。写"已处理 30 条,跳过 70 条""覆盖率 31%",
不写"处理得很好""覆盖率达标了"。验证器不需要解读,只需对照条件打勾。

若这个 harness 有周期性节奏(每周复盘、每月对账),再补 `plans/` 承接下发的计划,
形成闭环:`plans/` 下发 → 技能执行 → `state/` 回报 → AGENTS.md 里的调整规则决定下一轮 `plans/`。

**产出**:`state/STATUS.md`、`state/TODO.md`、`state/<task>/progress.json`、(按需)`plans/`
**卡点**:状态是内外两层之间**唯一的桥**。缺了它,每次开会话都是白纸,
Agent 也无法判断该调整什么——"下一步做什么"就只能靠人每次重新交代。

## 交付前自检

逐条打勾,任一条不过回对应段落:

- [ ] 新机器 `git clone` + `bash setup.sh` 就能用?(四)
- [ ] `AGENTS.md` 在 50–200 行,且没有任何细节只有指路?(一、二)
- [ ] 完成条件全部能用是/否判定,且有脚本执行?(二、五)
- [ ] 每条规则都有 Rationale 和优先级?(三)
- [ ] docs/ 里每份外部知识都在 SOURCE.md 有一行且有更新机制?(三)
- [ ] 每个外部环境都写清了怎么连、干什么、权限边界、凭据在哪?(四)
- [ ] 确定性判断没有一条留在提示词里?(五)
- [ ] `state/` 里只有原始数据,没有自我评价?(六)
- [ ] 从零走一遍真实任务,产出符合预期?(全)

## 用完之后:持续固化

Harness 不是交付一次就完事。以后每次发现 Agent 反复犯同一个错:
在对话里试出有效做法 → **写进对应文件** → commit。
没有固化,改进永远是临时补丁;有了固化,每轮改进都在让它更完善。

腐化预警:入口文件开始频繁出现"但是""除非",或 Agent 跑偏时你对着规则列表
指不出错在哪 —— 进 `references/smells.md` 第 5 节做治理(优先级 → 矛盾检测 → 定期清理)。

## 参考(作业依据,不要向用户复述)

- `references/templates.md` — 全部文件骨架:AGENTS.md / SKILL.md / constitution / ADR / SOURCE / environment / STATUS / TODO / cron 登记表 / 验证脚本下单话术
- `references/smells.md` — 五个坏味道的诊断信号与重构手法(需求模糊、隐式约定、信息散落、虚假胜利、指令腐化)。**诊断既有 harness 时从这里进,不走六段**
- `references/concepts.md` — 双层循环、四子系统、计算型/推断型判据、六个最佳实践(每条附违反症状)
