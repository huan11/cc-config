# 坏味道与重构手法

> 坏味道 = Harness 中潜在的、影响输出质量、造成不稳定的特征。重构 = 有针对性地消除它。
> 诊断顺序:先看行为信号,再定位到子系统(前馈 / 反馈 / 状态 / 工具 / 环境),最后套手法。

| # | 坏味道 | 一句话本质 | 重构手法 |
|---|---|---|---|
| 1 | 需求模糊 | 把需要大量上下文的需求压进一句话,猜对是偶然 | 提取指令文件 |
| 2 | 隐式约定 | 规则只在人脑子里,Agent 拿通用方案套你的特有上下文 | 建立原则文档 |
| 3 | 信息散落 | 知识进了仓库但没更新,仓库变成"事实的旧版本" | 管理知识依赖 |
| 4 | 虚假胜利 | 惰性生成:跳过难的,自信宣布完成 | 分离执行与验证 |
| 5 | 指令文件腐化 | 只增不减,规则互相矛盾 + 中间迷失 | 指令文件治理 |

---

## 1. 需求模糊 → 提取指令文件(Extract Instruction File)

**成因**:倾向于一次性提示(one-shot)。厂商宣传强化了"总有一天 one-shot 就够用"的错觉,
但那些惊艳的 demo 大多是**成熟已知系统或其变体**(贪吃蛇、3D 贪吃蛇);
你脑子里的"背单词系统"含周计划、记忆曲线、复习节奏、三个模块,而说出口的只有三个字。

**诊断信号(严重程度递增)**
1. Agent 反问"这里我应该怎么做?"——你留了太多言外之意。
2. 交付的东西**看起来对、用起来不对**——猜对了表面,没猜对本质(它理解成"随机抽问",你要的是"周计划 + 记忆曲线")。
3. 验收时你反复说"我不是这个意思"——最严重。这不只是信息缺失,还有**优先级丧失**:
   对话中的修正对 Agent 权重相同,它分不清哪条是核心约束、哪条是随口一说,于是试图同时满足全部,顾此失彼。

**手法**:把零散描述提取为结构化指令文件,必须含**约束条件 / 完成条件 / 边界情况**三块。
> one-shot 效果特别好的提示词,绝大部分也都含这三块。差别只在 Harness 会反复执行它。

**三步落地**
1. `基于我们之前的讨论,你理解的需求约束条件有哪些?逐条列出。` + `你还有哪些需要澄清的地方,以问题形式逐条列出。` → 写入 AGENTS.md。
2. `针对当前任务,你怎么知道做完了?验收标准是什么?` → 若答"你说没问题就算完"= 完全没标准;若列的和你脑子里不一样 = 有歧义。补真实标准,写入 AGENTS.md。
3. 从约束条件里**拆出边界情况单独写**("每天 10 个新词"是约束,"连续答错 3 次降低次日配额"是边界)。好处:Agent 不会把边界当常规流程、主流程更显眼、优先级明确、人也更容易发现自己漏了什么。

## 2. 隐式约定 → 建立原则文档(Establish Principles)

**成因**:需求清楚了,但 Agent 不了解**实现方式的约定**。A 模块必须走中介层(两年前直连出过一致性事故),
B 模块用 XML(兼容一个停产的第三方系统)。这些不是需求,是带历史权衡的约定。
难点不在知识本身,**而在优先级**——不同模块有不同的取舍。

**诊断信号**
- Code Review 时你反复说"这里应该用我们约定的方式"——不是偶然失误,是约定没写下来。
- Agent 迟迟做不完某个功能,因为它在**从头发明解决方案**。

**手法**:不是给一本"每个模块怎么做"的操作手册(规则清单),而是给**决策框架**——
回答"当 X 和 Y 冲突时优先选哪个"。Agent 到一个模块先自问:这个模块的核心约束是一致性优先还是可用性优先?
兼容性优先还是功能演进优先?再推导正确行为。

**优先层级(高 → 低)**
1. **不可协商的红线**:安全合规、数据保护、法律要求。任何情况不得违反,用户当面要求也不行。
2. **用户当面的指令**:能覆盖项目级规则和模块级权衡,不能覆盖红线。
3. **项目级约定**:AGENTS.md / constitution.md 里的全局规则。
4. **模块级约定**:模块 ADR,记录当时的权衡依据。
5. **最佳实践**:通用建议,冲突时可让步。

**文件结构**:AGENTS.md(入口层,只说"有宪法、在哪、何时读")→ docs/constitution.md(原则层,红线/规则/建议,**每条带 Rationale**)→ docs/decisions/adr-*.md(模块层,上下文-决策-权衡-影响)。
入口层不写原则本身,这样它不会随原则增多而膨胀。

**存量项目省力办法**:让 Agent 多轮阅读源码、测试套件、CI 流水线,把约定提取成宪章草稿,再人工裁剪。

## 3. 信息散落 → 管理知识依赖

**成因**:仓库里的信息是静态的,现实是动态的。词表在改、依赖在升级、业务规则在变,
差距每天扩大。**过时的文档比没有文档更危险**:没文档时 Agent 知道自己在猜,你会检查;
有过时文档时,Agent 自信地精准实现了错误目标——**执行到位,方向全错**,而这份自信来自你建的仓库。

真正的障碍是:决议往往形成在 Agent 系统之外(邮件、会议、线下讨论),
把它固化回仓库是一个**额外动作**,而额外动作最容易被遗忘。

**诊断**:不用等信号,这是默认最佳实践。只要 Harness 依赖外部信息源,就该建主动更新机制。

**手法**
- 有 URL / API 的源 → 建 `docs/SOURCE.md` 登记「仓库文件 → 外部来源 → 更新时机」,
  再做一个 `sync-sources` 技能:读 SOURCE.md → 拉取 → 与本地 diff → 有差异则更新并提 PR(附更新摘要) → 标"按需"的源每次询问用户 → 支持手动触发和 cron。
- 没有固定来源的源(如自己维护的词表) → 在 AGENTS.md 加会话开场提醒:
  "先问用户:XX 列表是否有更新?若有,更新对应文件与计划,并告知用户;若无,继续正常流程。"

**类比**:仓库里每条外部知识都是一条**知识依赖**,外部源变化就像依赖库发了新版本,
该像 Dependabot / Renovate 那样及时升。信息源多且变化快时用现成的知识库工具(如 OpenWiki 这类带 Gmail/Slack/Notion 连接器的 CLI),少而稳定时 SOURCE.md + 定时技能就够。两者不互斥,可先手动后迁移。

## 4. 虚假胜利 → 分离执行与验证(Separate Execution from Verification)

**成因:惰性生成(Lazy Generation)**——过早终止任务,系统性回避需要更多推理的部分,
只做容易的,然后对整个任务自信宣布完成。三个特征:
1. 容易的部分做,而且做得**很快**;
2. 复杂的部分跳过,**但不告诉你跳过了**;
3. 把自己完成的部分当作全部,自信交付。

模型层面的原因:**位置偏差**(对上下文开头和结尾注意力最高,中间最容易被忽略)+ **难度回避**(没把握或算力开销大就跳过)。

**为什么设了终止条件也失效**:① **过度自信**——被要求自评时系统性给出正面评价,
模型报告的置信度显著高于实际准确率,它倾向于赞同"我已做完"而不是推翻它;
② **认知统一**——生成和评估由同一个 Agent 执行,生成时的上下文、假设、盲点原样保留到评估阶段,
它只能确认自己之前的判断。

**诊断信号**
- 抽查时持续发现工作量数据不符(要求 100 条只交 80 条;要求背 30 词只给 10 几个)。
- **完成得异常快**——任务越复杂完成越快,越值得警惕。需要综合多份资料的活儿不到一分钟交稿,大概率只做了最容易的部分。

**三步落地**
1. **完成条件定义为可验证指标**:非 IT——"100 条全部处理,每条有分类和严重程度标注";IT——"覆盖率 ≥90%,端到端全过"。每条都能用是/否判定。
2. **要求记录进度,而不是汇报结果**:只写原始数据——"已处理 30 条,跳过 70 条"+ 跳了哪些、为什么跳;写"分支覆盖率 31%",不写"覆盖率达标了"。验证者不需要解读,只需对照条件打勾。
3. **让独立验证者读进度并判断**:脚本 / 检查清单 / 另一个人 / 另一个被调校得挑剔的 Agent。
   在 AGENTS.md 声明:"你负责执行并记录进度,完成判断由验证者根据进度数据决定,你不能自行宣布完成。"

**最佳形态是脚本**:只读 state/ 里的数值字段,不解析任何对话内容或 LLM 生成的主观描述;
输出 PASS / FAIL + 具体指标 + 当前值。判断逻辑写成代码 = 把验收标准变成可重复执行的测试套件,
"我觉得达标了"在脚本面前没有立足之地。

## 5. 指令文件腐化 → 指令文件治理(Instruction File Governance)

**成因:只增不减**。每条规则加进去的时候都是有效的(Agent 犯错→加规则→不再犯,这是真实改进)。
问题出在累积之后:
- **优先级冲突与矛盾累积**:规则是一条条写的,写时只面对一个场景;Agent 执行时同时面对全部规则。
  "尽快""适当""必要的时候"这类词放在不同规则里可能指向相反行为。
  5 条规则的手册每条都重要,300 条的手册重要规则被淹没,Agent 只能靠猜。
- **中间迷失(Lost in the Middle)**:开头记得牢、结尾记得住,埋在中间的最容易被忽略。
  最典型的受害者是安全约束——它往往写在文件中部,被日常规则淹没。

**诊断信号**(不看行数!50–200 行都算健康)
- 指令文件里频繁出现"但是""除非"——规则在互相打补丁,文件已失去秩序。
- Agent 背离预期时,你对着长长的规则列表**无法指出错误根源**。

**手法**:先把结构建好(分层:入口只做说明,细节按需读取;规则用决策记录 ADR 或一张**规则登记表**描述),
然后**持续维护**——重点在后者,建好而疏于治理会再次膨胀。维护三件事:

1. **优先级确定**:每条规则明确优先级(沿用上面的五层)。它是整个机制的基础——
   矛盾检测靠它裁决谁胜出,定期清理靠它决定先删哪条。没有优先级的规则列表,和散落的文字没区别。
2. **矛盾检测**:做成技能 + 定时任务(或每次会话开场检查一遍)。
   逐对检查**适用条件是否重叠**(只有重叠才可能矛盾)→ 判断行为是否互斥 →
   裁决:优先级高的胜出,同级看谁更接近当前现实,裁决不了的标"待人工"升级给人。
   > 矛盾本身不可怕,可怕的是它一直隐藏着,让 Agent 每次随机选一条。显式矛盾可处理,隐式矛盾只能靠运气。
3. **定期清理**:登记表里的**过期条件**就是为清理准备的——没有过期条件的规则永远不会被删。
   Agent 列出过时/冗余/矛盾条目 → 人确认删除 → **删除留痕**(标 deprecated 而非直接消失),
   以后审计还能看到曾有这条规则以及它为什么被删。
