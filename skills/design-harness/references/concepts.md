# 概念参考:双层循环、四子系统、六个最佳实践

## 1. 双层循环模型

Harness 的概念模型。它的作用是指导拆解:哪些映射到流程,哪些映射为子任务。

### 外层:PDCA
适用于**有规模的任务**——构建一个完整系统、按报税流程准备全部资料。
关键在于先构造一份计划,把大任务拆成可执行步骤,逐项追踪,**每步验收通过再进下一步**。

- Plan:总量、周期、节奏(200 词 / 4 周 / 每天 10 个)
- Do:一次执行单元(每天一个学习会话 + 测验)
- Check:什么节奏查、查什么指标(每周查掌握率、遗忘率、哪类词性易忘)
- Act:指标到什么值就怎么调(错误率 >60% → 下周重点复习动词;遗忘率 >20% → 新词配额 10→7)

没有 PDCA,这类任务一定失控——上下文限制、注意力漂移、复杂上下文中推理能力下降。

### 内层:操控循环(Steering Loop)
适用于**上下文明确、一次能生成的子任务**。这类任务拆得更细也不会更好,重点是
"把上下文交代清楚 + 约束模型行为"。四段:

| 环节 | 干什么 | 常见形式 |
|---|---|---|
| **前馈 Feedforward / Guides** | 行动前引导,提高第一次就做对的概率 | 参考文献、提示词、原则说明、开工前置条件、输出格式 |
| **行动 Action** | 在前馈约束下执行 | — |
| **反馈 Feedback / Sensors** | 行动后观察结果 | 测试、静态分析、日志、检查清单 |
| **调整 Steer** | 据反馈决定是否继续 / 重做 / 问人 | Agent 自我纠正在发挥作用 |

**前馈和反馈缺一不可**:只有反馈 → Agent 会重复犯同一个错;只有前馈 → Agent 会过于草率地结束任务。

内层是更重要、也更值得投资的能力。技能(Skill)已成为封装与分发 Harness 的统一格式,
多 Agent 编排差不多就是 Skill 编排,而 Skill 编排可以靠前馈控制实现——**驾驭工程对编码能力的要求大幅下降了**。

## 2. Agent 的内置 Harness

要驾驭的对象是 Agent 内部已经在转的循环:

- **推理行动循环(ReAct)**:推理 → 行动 → 观察。没有它,Agent 只是静态文本生成器。
- **自我纠正循环(Self-Correction)**:推理 → 行动 → 观察 → 自我纠正。每轮检查输出是否满足质量标准(格式、约束、数据完整性),不满足就重新生成/补充/问人。

自我纠正循环本身就是一个戴明环("推理-行动"是 PD,"观察-自我纠正"是 CA),
它就是**内置 Harness**,是驾驭的主要对象。**指令子系统驾驭的正是这个循环。**

## 3. 四个子系统

| 子系统 | 作用 | 服务于 | 载体 |
|---|---|---|---|
| **指令 Instructions** | 告诉 Agent 做什么 | 直接驾驭自我纠正循环(前馈 + 反馈) | AGENTS.md、constitution.md、SKILL.md |
| **工具与技能 Tools & Skills** | 给 Agent 做事的途径 | 引入计算型控制 | scripts/、skills/、MCP |
| **环境 Environment** | Agent 运行的真实条件 | 保证反馈信号可信、可复现 | requirements.txt、setup.sh、锁版本 |
| **状态 State** | 让 Agent 记住过去 | 前馈与反馈之间的桥、转向的依据 | plans/、state/、git 历史 |

要点:

- **指令子系统优先级高于单次提示词**。用户可在对话中追加需求,但不能覆盖 AGENTS.md 的核心规则——这也是它被称作 Agent 宪法(Constitution)的原因。
- **技能 ≠ 工具**。工具是手和脚,让 Agent 能做一件事;技能是 App,内含独立的工作流程和 Harness,让 Agent 知道"什么场景该用什么流程"。技能 = 一组指令 + 工具 + 验证规则的封装。
- **环境的核心是可复现性**。反馈控制的结果只在一致的环境中才有意义;环境每次都不一样,反馈信号就不可信,输出就不稳定。
- **状态的设计很像系统建模**。形式可以很简单(一个 reports/ 目录),也可以很复杂(数据库),按任务取舍。

## 4. 计算型 vs 推断型

大模型今天只有两种能力:推理、工具调用。对应两种控制:

| | 推断型 Inferential | 计算型 Computational |
|---|---|---|
| 靠什么 | 大模型的推理能力 | 代码 / API(靠工具调用触发) |
| 确定性 | 非确定 | 确定,同输入同输出 |
| 适合 | 语气是否合适、风险是否说透、逻辑是否自洽、翻译是否通顺 | 链接是否返回 200、字数是否 ≥300、间隔重复调度、覆盖率阈值 |
| 成本性质 | 每次调用都烧 token(灵活开销) | 一次编写、无限次运行(固定开销) |
| 用错的代价 | 用模型算小学数学:又慢又贵,还可能因上下文偏移漏数 | 用规则判断语义:枚举不完,换个句式就不匹配,从诞生起就腐烂 |

最佳配比:**代码处理 60–70% 可形式化的检查,模型覆盖剩下 30–40% 需要语义理解的情况**。
这不是技术选择,是成本最优解。

技能正文里**不必写明调用哪个函数**——把工具的用途说清楚,让 Agent 自己推断更好:
写死函数名能省一点 token,但工具一改就得手动改引用。

## 5. 六个最佳实践

诊断"时好时坏"时逐条对照,往往能定位到具体违反了哪一条。

### ① 双层循环模型(Dual-Loop)
外层管流程与进度,内层管执行质量与自我修正。进行不顺时停下来用它重新想一遍当前问题。
**违反症状**:Agent 与 Skill 权责边界不清,每个技能里都抄了一份计划调整规则,执行结果偏移。

### ② 仓库即规范(Repository as Spec)
仓库是唯一事实来源;不在仓库里的对 Agent 等于不存在。换人、换机器、换 Agent 系统,
只要仓库同一个,行为就一致。仓库还留下可追溯的变更轨迹(改了什么、为什么、结果如何都在 git commit 里),
而不是靠人的回忆或聊天记录。**设计要 Agent-first**,服务导航效率,不服务人的完整阅读体验。
**违反症状**:同一件事今天在对话里说一遍、明天再说一遍,输出忽好忽坏。

### ③ 渐进式信息披露(Progressive Disclosure)
入口文件只写核心规则和路径指引,走到哪一步再加载哪一步的上下文。
根因是模型的两个硬限制:**上下文窗口有上限**(无关内容会把重要指令挤到窗口边缘,被截断或压缩,
于是 Agent 跳步骤、忘子任务)和**注意力分配不均匀**(即使窗口够大,注意力会被稀释,
关键指令的响应质量逐轮下降)。
> 把大模型当 ADHD 患者,首要任务是帮它保持注意力。
**违反症状**:上下文倾倒,长会话里越做越离题。

### ④ 分离计算型与推断型
见上节。**违反症状**:让模型数条目、算日期、比阈值,结果每次不一样;或写了一堆维护不了的条件分支去判断语义。

### ⑤ 最小干预(Least Intervention)
把重复的、可预测的检查自动化,让 Agent 自己发现并修正,而不是让人充当 Sensors。
人工检查看似"只是看一眼",但**上下文切换的成本远高于阅读时间**;次数一多,
大部分人会放弃参与、盲目接受结果,几小时后再抱怨 Agent 不行。
坚持人工反馈的结果是——**人成为系统里最慢的瓶颈**。
> 反馈循环应该让问题在到达人眼之前就自我纠正;好的驾驭机制不追求消除人类输入,
> 而是把人类输入引导到最重要的地方。(Martin Fowler)
**违反症状**:每轮都要人读产出、指错、组织语言让它改。

### ⑥ 可复现性优先(Reproducibility First)
引入计算型控制后,输出质量 = 模型能力 + 代码质量的叠加,而代码依赖的环境、库、工具都会影响结果。
类比可重现构建、不可变基础设施:锁死环境。
**违反症状**:用得好好的 Agent 无端变差、同事机器上判若两人——先查环境配置,别只怀疑提示词和模型。
