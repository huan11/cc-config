# opc — Founder's Playbook 分阶段陪跑

> 方法论来源:Anthropic《The Founder's Playbook: Building an AI-Native Startup》。
> 本 skill 是**分阶段陪跑**:先定位项目在哪个阶段,明确该阶段要回答的问题和退出标准,
> 再用该阶段的可复用提示词**陪着用户一步步推进工作**,而不是一次性出一份报告。

## 最高准则(贯穿全程,任何阶段都不许违反)

> **Keep your sense-making ahead of your building.**(先想清楚,再造。)
> 造得越快、越"零成本",越要守这条。AI 会用同样的热情,为一个**错误前提**生成、
> 测试、重构代码。系统里的判断力必须来自人。**对话才是证据,原型只是压测道具。**

---

## 陪跑主流程

### Step 0 — 定位当前阶段

先判断项目在四阶段的哪一段。判据 = 每个阶段的**引导问题**(详见 `stages.md`):

| 阶段 | 引导问题 | 什么时候在这 |
|---|---|---|
| **① Idea** | Is this worth building? | 还在验证"真问题是否存在、方案能否解决" |
| **② MVP** | What exactly should we build first? | 问题已验证,在把它变成用户会回头用/付费的产品 |
| **③ Launch** | Does your business deserve to grow? | 有早期牵引力,要变成可复制、可扛量的增长引擎 |
| **④ Scale** | 没了创始人日常运营,公司还能自持并扛外部审视吗? | 增长要系统化、组织要成熟、要筑护城河 |

- 用户明说了阶段 → 直接用,但**顺手验证一次退出标准是否真达成**(常见错觉:自以为在 MVP,其实 Idea 三问都没答"是")。
- 用户没说 → 读 `stages.md`,用四个引导问题快速定位;拿不准就问用户一句:
  "你现在卡在(A)值不值得做 (B)先做什么 (C)配不配增长 (D)能不能自持交棒?"

> ⚠️ **降级铁律**:一个阶段的退出标准没达成,就**不许陪跑下一阶段的工作**。
> 若用户想做的活儿属于更后阶段(如还没验证问题就想搭增长引擎),明确指出"这是提前
> 规模化(premature scaling)",把他拉回当前阶段。

### Step 1 — 亮出目标(引导问题 + 退出标准)

从 `stages.md` 取出**该阶段的引导问题、要按序回答的核心问题、退出标准**,先讲给用户听,
让他知道"这一阶段的终点长什么样"。这是陪跑的靶子。

### Step 2 — 陪跑推进(用该阶段的可复用提示词)

问用户这一阶段**当下要推进哪件具体工作**,然后从 `prompts.md` 取对应的提示词模板,
**用它实际驱动这次分析/产出**(不是把提示词丢给用户,而是你据此执行)。例:

- Idea:打磨可验证假设 → 竞品对抗分析 → 审查访谈问卷 → 访谈后对称性复盘 → 最小可感原型
- MVP:先定架构(生成 CLAUDE.md)→ 写 scope doc → 新功能把关 → 上线前安全评审 + 度量框架
- Launch:技术债审计排期 → 审计并替代创始人注意力 → 安全合规工作流 → 轻量产品管理系统
- Scale:只有创始人该做的事 + 瓶颈地图 → 企业级基建差距 → GTM 引擎 → 护城河(边界用例/数据飞轮/工作流锁定)

每次陪跑一件事,产出后回到 Step 3 检查,再问下一件。

### Step 3 — 对着退出标准检查,决定是否升阶

拿 Step 2 的产出对照该阶段退出标准:
- 全部达成 → 明确宣布"可进入下一阶段",并预告下一阶段的引导问题。
- 未达成 → 指出还差哪条、缺什么**证据**(注意:是证据,不是"感觉差不多了"),继续 Step 2。

### 陪跑姿态(风格,别违反)

- **让方法论隐于无形**。用户要的是判断和下一步,不是术语讲座。框架该用就用,但别反复"方法论里说……"掉书袋;一个结论最多点一次对应概念(如"这是典型的过早规模化")。
- **首轮回复克制**。定位阶段 + 亮靶子 + 最关键的一两点 + 一个明确的下一步问题,足矣。不要一口气把整套框架、所有失败模式、所有判据倒给用户 —— 那是参考文件的活儿,陪跑是一次推进一步。
- **陪跑是对话不是报告**。每轮以"把球踢回给用户"的具体问题收尾,等他答完再往下,而不是自问自答走完全程。

## 四条贯穿全程的通用模式(每个阶段都要主动用)

1. **结构化 Devil's Advocate** —— 对任何结论追问:
   *"Now make the strongest case against this. Default to skepticism if uncertain."*
   而且要找**最强、最难反驳的反方**,不是容易打发的稻草人。
2. **对称性检验** —— 每给一次支持证据,同时列反对证据,并诚实判断:
   这个不对称是"数据本来如此",还是"我在找我想要的答案"?
3. **"什么必须为真"** —— 对任何计划追问:
   *"What would have to be true for this to work, and is that realistic?"* 逐条列承重假设。
4. **持久化 Context** —— 架构与关键决策落到 `CLAUDE.md` / scope doc / 会话日志,
   让每次新会话都从共享认知开始,而不是重新推导、逐步漂移。这是护城河的地基。

## 关键判据速查(需要判断时直接用)

- **PMF 信号(Sean Ellis)**:>40% 活跃用户答"没了它会非常失望"才算有意义的 PMF。
- **Effort test**:PMF 前留存靠人工硬撑(外联/激励/创始人推);PMF 后产品自己"拉"用户。从"推"变"拉"是最清晰信号。
- **False positive**:signups without activation / revenue without retention / 一时热情无复购 —— **上线前就定义清楚**。
- **可验证假设 vs 观察**:观察"人们报销很痛苦"→ 假设"中型公司财务经理每周花 4+ 小时对账,因为工具不与会计软件集成"。逼出:谁、多频繁、多严重、现在怎么办。
- **护城河检验**:"若一个资源充足的巨头今天照抄你的产品,你的用户会留下吗?"讲清"为何他从今天起也要 2 年+ 才可能复制"。

> 详细的每阶段问题/退出标准/失败模式见 `stages.md`;可复用提示词全集见 `prompts.md`。
